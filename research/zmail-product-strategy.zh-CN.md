# Zmail 产品策略讨论稿

2026-11-17 · 供创始团队决定下一季度投入。竞品证据来自官方产品资料，客户需求、付费意愿和下列目标均待试点验证。

## 愿景、使命和首批用户

愿景是让小团队也能放心地用自己的身份与客户通信，无论写邮件的是员工、应用，还是受托办事的 AI。使命是让团队在 zmail.im 接入自己的域名和发信服务，从一封邮件查到谁发起、厂商如何处理、客户如何回复，以及接下来该由谁处理。

优先服务已经用邮件跟进客户的 SaaS 和 AI 产品团队。开发者接 API，运营或客服在网页跟进，买单的人通常是负责客户体验和工程投入的团队负责人。这是首批访谈对象的选择，购买角色仍需核实。首个场景选服务开通后的跟进：应用发出欢迎邮件，客户回复配置问题，团队成员或被授权的 Agent 接手。这个场景同时检验发件身份、收件和协作，用户也容易判断它有没有解决问题。

## 产品从哪里出发

现有部署使用 Cloudflare，已验证正式发件域名、品牌模板、真实投递事件和双向收发。一封品牌邮件在 Gmail 的三项认证均通过。生产自助注册仍关闭，适合先邀请团队。验收计划覆盖联系人、广播和 API 等场景，列入计划的功能仍要逐项看验收结果。底层 FastBuild 有独立的框架愿景。部署验收（`docs/DEPLOYMENT_FE5_0083.md`，未纳入版本库） · [产品验收计划](../docs/testing/ACCEPTANCE_TEST_PLAN.md) · [框架愿景](../docs/VISION.md)

## 竞品和客户已有的选择

| 客户会选谁 | 官方资料显示的能力 | 对 Zmail 投入的影响 |
|---|---|---|
| Resend，开发者给应用加邮件 | SDK、REST、SMTP、测试模式，首页直接展示首发代码。 [Resend](https://resend.com/) | 新用户应该能复制示例并在控制台找到同一封信。也可把 Resend 作为客户自带的服务。 |
| AgentMail，给 Agent 一个邮箱 | API 创建收件箱、收发邮件、按线程读回复，也支持转人工。 [AgentMail](https://www.agentmail.to/) | 双向通信和人工接手已有直接竞争。试点要检验客户是否特别需要保留自己的厂商、品牌和权限。 |
| Postmark，运营交易邮件 | 用 Message Streams 将交易邮件和广播拆开投递。 [Postmark](https://postmarkapp.com/message-streams) | 保住系统通知的信誉有独立价值。给正式身份、共享试用地址和营销用途设清晰边界。 |
| Novu，跨渠道通知和对话 | 提供通知工作流、产品内收件箱和双向沟通。 [Novu](https://www.novu.co/) | 同时需要短信、推送的客户已有成熟选择。优先把邮件从发送到处理回复的体验做好。 |
| 继续用现有厂商加团队邮箱 | 在访谈中请对方演示现行做法，记录一次查信和交接实际耗时。 | 这是试点的对照组。如果原有做法已经足够，新增一个控制台的迁移成本难以成立。 |

产品判断是把厂商作为可选的投递服务，把发件身份、往来记录和团队处理流程留在 Zmail。最有价值的验证是让一个已有厂商账号的团队完整处理一段真实往来，再观察它下周是否继续使用。单纯统计连接器数量解释不了留存。

## 遇到取舍时怎么决定

- **发件身份归客户。** 共享域名适合试发。正式业务引导验证客户自己的域名，更换厂商时先验证同一身份，再切换后续邮件。
- **状态如实可查。** 分别呈现提交成功、对端服务器接收、退信和客户回复。厂商只提供提交回执时明确显示证据到哪一步。
- **自动化可托付。** 给 Agent 授予指定邮箱和动作的权限，团队能查操作、撤销授权并接手会话。优先支持客户主动触发或已同意的往来。
- **尊重收件人的选择。** 投诉、退订和永久退信应在适用范围内跨厂商生效。客户更换服务时仍沿用原有约束。

## 90 天开发顺序与决策条件

| 时间 | 建议投入 | 如何决定下一笔投入 |
|---|---|---|
| 第 1–2 周 | 产品负责人访谈 8 个团队，其中 4 个有 Agent 场景、4 个以应用通知为主。请每人演示最近一次查投递或交接回复，记录厂商、耗时、权限、损失及现行账单。用现有邀请制部署观察首次发送。 | 至少 3 个团队同意用真实域名和一个业务流程试点。若主要困难集中于 DNS，就先修域名引导。 |
| 第 3–6 周 | 建议先做一个完整的第二厂商接入。默认候选 Resend API，若试点团队集中使用其他厂商则调整。网页按组织配置凭据，测试域名、发信和回执，记录每封信使用的厂商。SMTP 提供兼容入口，界面按实际可用事件展示。 | 两个独立组织各完成一次真实发送、回复与故障排查。模拟超时后重试，确认不会在结果未知时换厂商重复发送。 |
| 第 7–12 周 | 将回复归入原会话，支持指定人员或 Agent 接手，补齐受限凭据、操作记录和退信处理。邀请试点按周使用，并用真实报价验证付费意愿。 | 建议以 3 个团队连续 4 周使用、至少 2 个接受付费试点作为扩投条件。若使用集中在单向通知，则按使用记录调整协作功能投入。 |

**核心指标**选每周完成真实业务邮件往来的组织数。同一组织一周计一次，要求业务邮件和对应客户回复可以关联，剔除内部测试。另记单向通知活跃组织，避免漏掉另一类需求。首发耗时从已获邀用户进入控制台到第一封测试信拿到回执，DNS 等待单列。并行观察每千封永久退信及投诉数、重复投递数和无法关联的回复数。先建基线，再决定是否扩大注册。

**商业假设**是客户直接向厂商支付发送费用，向 Zmail 支付组织订阅，换取团队处理回复、权限和可追溯记录。在试点中分别向负责人出示单邮箱和团队协作方案，记录真实采购决定及拒绝理由。若只有低价转发获得兴趣，就重新评估客户群与订阅价值。公开获客、头像、更多厂商和多渠道扩展，可在留存与付费证据形成后重新排序。
