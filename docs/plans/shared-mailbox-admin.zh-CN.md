# 组织管理后台：公共邮箱管理（第一期）设计

状态：已实现（feat/shared-mailbox-admin；验收流程 api/tests/kest/mailbox_admin.flow.md）
依赖：PR #22（邮箱访问权限）、PR #23（发送队列）、自助域名分支。这些合入 main 后从 main 开发；若开工时仍未合入，就叠在 `feature/mailbox-organize`（它已包含 #22、#23）上开发，自助域名合入后再变基（我的决定）。

## 1. 目的

Zmail 是 PaaS：每个客户组织都有两个端。

- **客户端（C 端）**：员工收发邮件的工作台，即现在的 `/console/mailboxes`。
- **组织管理后台**：组织所有者和管理员管理本组织的邮箱、域名、成员。对标飞书"管理后台 → 邮箱 → 地址管理 → 公共邮箱"。

仓库里的 `admin/` 工程是 Zmail 平台运营方自己用的后台，不给客户用，本设计不碰它。

现在给公共邮箱建账号、加成员的入口都在员工工作台里，几十个公共邮箱时没法集中看、批量建。第一期补上组织管理后台的骨架和"公共邮箱"这一页。

## 2. 目标、非目标、反目标

目标：

- web 里新开组织管理后台区域，只有组织所有者和管理员能进，布局参照飞书管理后台（左侧导航 + 内容区）。
- 公共邮箱列表：名称、地址、成员数、24 小时内已发封数；按名称或地址搜索；分页。
- 页面顶部显示组织发信总额度（"24 小时已发 37 / 200"）。
- 每行操作集中：编辑名称、管理成员、删除。
- 新建公共邮箱。
- CSV 批量导入（先预览、再确认）和导出。
- 每组织邮箱数上限改为可配置（已确认）。

非目标：

- 按邮箱单独的发信上限（已定：只显示已发数）。
- IMAP/SMTP、邮件组、群邮箱、邮箱回收站、邮箱搬家、安全与反垃圾、数据合规（后续期）。
- 个人邮箱的管理页（后续期，结构相同）。
- 导入时自动发组织邀请（已定：标错，先去邀请）。
- 用导入修改已存在的邮箱。

反目标：

- 管理员借管理后台读到自己不是成员的公共邮箱里的邮件（#22 规定管理员能看元数据、不能读信）。
- 预览说能建、确认后却建失败的行很多（预览必须和真正创建走同一套校验）。
- 员工工作台因为组织邮箱多了而变慢或出现一堆自己用不了的邮箱。

## 3. 已确认的决定

- 发信统计只显示已发数，不新增按邮箱上限。
- 导入时不在组织里的成员：该行标错"不在组织中，请先邀请"，其他合格行照常创建。
- 方案 A：服务端导入（预览 + 确认），导出由 web 服务端生成。
- 组织管理后台放在 web 里（PaaS：客户的管理后台和 C 端都在 web；`admin/` 是平台方的）。
- 每组织邮箱上限改为可配置，默认 50，最多 5000。

## 4. 方案对比

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A（采用）** | 新增导入接口，`dry_run` 预览与正式创建共用同一套逐行校验；导出由 BFF 按列表接口分页拼 CSV | 预览可靠，规则只有一份；多一个接口 |
| B | 浏览器解析 CSV、比对成员、逐行调用现有建邮箱接口 | 后端几乎不改；但预览看不出地址被占，几百个请求中途失败留半成品 |

## 5. 设计

### 5.1 管理后台区域（web）

- 路由前缀 `/console/admin`，单独布局：左侧导航"域名管理""公共邮箱"，后续期在这里加项。
- 非所有者、管理员访问：和现在其他受限页面一样返回 404。
- 现有 `/console/mail-domain` 移到 `/console/admin/domains`，旧地址重定向（我的决定：域名是管理后台的事）。
- 员工工作台顶部给所有者、管理员显示"管理后台"入口。
- 文案走 `web/src/i18n/modules/…/{en-US,zh-Hans}.ts`。

```
┌──────────────┬────────────────────────────────────────────────┐
│ 管理后台      │ 公共邮箱                 [导出][批量导入][创建] │
│ 域名管理      │ 24 小时已发 37 / 200                            │
│ ▸公共邮箱     │ [搜索名称或地址…]                               │
│              │ 名称   地址               成员  24h已发  操作    │
│              │ docs   docs@zgi.ai          5      0    编辑 ⋯  │
│              │ business business@zgi.ai    1     12    编辑 ⋯  │
│              │                            ‹ 上一页  下一页 ›   │
└──────────────┴────────────────────────────────────────────────┘
```

### 5.2 列表接口

- 新增只给所有者、管理员的列表接口（名字由契约定，例如 `GET /v1/mailbox-directory`），与员工用的 `GET /v1/mailboxes` 分开，后者不增加开销。
- 参数：`type`（`shared` / `personal`，第一期页面只用 `shared`）、`q`（名称或地址子串，忽略大小写）、游标分页（遵循 `contracts/README.md` 的 cursor 规则），按创建时间倒序。
- 每项：现有邮箱元数据 + `member_count` + `sent_last_24h`。
- `sent_last_24h` 口径与组织额度完全一致：滚动 24 小时内该邮箱的发信尝试次数，失败的和群发的也算；列名用"24 小时发信次数"而不是"已发送"（我的决定）。已删除邮箱的发信仍计入组织总数，所以各行相加可能小于顶部总数，页面上加一句说明。
- 响应 `meta` 带组织级 `daily_send_limit` 和 `sent_last_24h`。
- 不返回任何邮件内容。

### 5.3 员工工作台的邮箱列表

上限放开后，所有者、管理员在 `GET /v1/mailboxes` 里会看到全部邮箱（#22 的规则），工作台会被几百个用不了的邮箱塞满。改为：`GET /v1/mailboxes` 新增可选参数 `scope=usable`，只返回调用者能读或能发的邮箱；工作台用它。不带参数时行为不变（我的决定，向后兼容）。

### 5.4 每组织邮箱上限

- `MaxMailboxesPerOrganization = 50` 改为配置 `MAILBOX_MAX_PER_ORGANIZATION`，默认 50，范围 1–5000（已确认）。
- 现在依赖"最多 50"的地方都要改：`GET /v1/mailboxes` 的有界列表注解、成员可见邮箱查询、封存查询、建邮箱时的计数。不带 `scope` 的 `GET /v1/mailboxes` 在上限大于 50 时仍需返回完整结果，实现时决定保留有界列表（上限即配置值）还是加分页。
- `GET /v1/mailbox-domains` 返回的 `max_mailboxes` 跟随配置。
- 配置调低到某组织现有数量以下时：已有邮箱不动，新建和导入返回已达上限（我的决定）。

### 5.5 新建、编辑、删除

- 创建：复用 `POST /v1/mailboxes`（`type: shared`），对话框里选域名、填本地部分、名称、成员（按组织成员选择，权限查看 / 发信 / 管理）。
- 编辑名称：需要新增修改显示名的接口（现有契约没有），只给所有者、管理员。
- 管理成员：复用 `PUT/DELETE /v1/mailboxes/:id/members/:user_id`，抽屉里列成员。
- 删除：复用 `DELETE /v1/mailboxes/:id`，二次确认，说明"邮件一并删除，地址永久保留不可再用"。

### 5.6 批量导入

CSV 格式（UTF-8，带表头，提供模板下载）：

| 列 | 必填 | 说明 |
|---|---|---|
| 邮箱地址 | 是 | `local@domain`，domain 为共享域名或本组织已验证域名 |
| 名称 | 否 | 显示名 |
| 成员 | 是 | `email:权限` 用 `;` 分隔，权限 `view`/`send`/`manage`，省略为 `send` |

- 浏览器只做 CSV 解析（列、编码），把行发给导入接口。
- 导入接口（例如 `POST /v1/mailbox-imports`）：一次最多 500 行；`dry_run: true` 只校验，返回每行的结果；`dry_run: false` 创建所有合格行，返回每行结果。
- 逐行校验与 `POST /v1/mailboxes` 完全相同：地址格式、保留地址、地址已占用（含本文件内重复）、域名可用、成员是组织成员（按账号邮箱匹配；匹配不到 → "不在组织中，请先邀请"）、成员 1–100、组织邮箱上限（按行序累计，超出的行标错）。
- 正式创建逐行独立事务：一行失败不影响其他行；结果页列出成功和失败，失败行可下载为 CSV 改好再导入。
- 预览与创建之间状态可能变化（别人抢了地址），以创建时的结果为准。
- 成员按邮箱匹配只在服务端做，接口只给所有者、管理员，不新增对外暴露成员邮箱的接口。

### 5.7 导出

- 导出由 API 生成（例如 `GET /v1/mailbox-exports?type=shared`，返回 CSV），只给所有者、管理员；BFF 只转发。这样成员邮箱只在服务端拼接，不需要逐个邮箱请求成员，也不新增返回成员邮箱的 JSON 接口（我的决定，替代原先"BFF 拼 CSV"）。
- 列同导入模板，再加成员数、24 小时发信次数、创建时间，文件名 `shared-mailboxes-YYYYMMDD.csv`。
- 成员列导出为 `email:权限`，与导入格式一致，便于导出改完再导入新邮箱。

### 5.8 审计

- 每个邮箱已有访问历史（`GET /v1/mailboxes/:id/access-events`，所有者、管理员可读）。创建、改名、成员增删改都记在对应邮箱的访问历史里；缺少的事件类型（如改名）在契约里补上（我的决定）。
- 导入本身不单独记汇总：每个新建邮箱各有一条"创建"事件，另外请求日志（`contracts/AUDIT.md`）自动记录导入请求。组织级的统一操作日志留到后续期。

## 6. 约束

- 只用 PostgreSQL；英文源码；品牌 Zmail；Zmail 是 PaaS，客户的管理后台和 C 端都在 `web/`。
- 契约先行：先改 `contracts/openapi.yaml` 和 `contracts/MAILBOXES.md`，oasdiff 检查兼容。
- 测试不发真信。
