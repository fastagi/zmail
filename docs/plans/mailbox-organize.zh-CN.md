# 邮箱整理、搜索与会话线程（P0 子项目 1）设计

状态：待确认（已含构建者审阅的回答）
依赖：PR #22（邮箱访问权限）与 PR #23（发送队列）。本子项目基于 `feature/send-quota-queue` 开发，二者合并后再合入 main。

## 1. 目的

#22 让员工能被分配公共邮箱，但邮箱里的邮件只有"已读/未读"和"删除"两个动作，没有文件夹、归档、搜索、线程。员工第一天拿来办公就会卡住。参考飞书邮箱和 mailflare（AGPL，仅参考设计，不复制代码），本子项目补齐"整理、搜索、看对话"这三件事。

P0 的另外两个子项目在本设计之后单独设计：

- 子项目 2（发信）：签名、撤销发送、定时发送、已读回执。
- 子项目 3（收信）：自动回复、外部邮件警示。

## 2. 目标、非目标、反目标

目标：

- 每个邮箱有固定位置：收件箱、已发送、归档、回收站，以及邮箱自建的文件夹。
- 邮箱自建标签，一封邮件可贴多个标签。
- 每人自己的星标。
- 列表按会话线程聚合，打开后看到整段往来。
- 在一个邮箱内按主题、发件人、收件人、正文搜索，中文可用。
- 列表上可多选批量操作。

非目标（本子项目不做）：

- 草稿箱、稍后提醒（snooze）、收信规则、垃圾邮件判定。
- 跨邮箱的统一搜索、搜索语法（`from:` 之类）。
- 文件夹嵌套。
- 第三方客户端（IMAP/JMAP）。

反目标（即便功能能用，也算失败）：

- 一个成员的整理动作越过 #22 的权限，例如只有"查看"权限的人能把团队邮件移进回收站。
- 线程把不相关的邮件错并在一起（宁可不并，不能乱并）。
- 搜索拖慢收件箱列表。
- 现有已读状态（每人一份）的行为发生变化。

## 3. 决定（来自讨论）

- 公共邮箱里，文件夹、归档、回收站、标签**团队共享**；星标和已读**每人各自**。
- 方案 A：状态挂在邮件上，线程是展示层的归组。

## 4. 方案对比

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A（采用）** | 邮件表加位置、文件夹、回收时间、线程字段；标签用关联表；星标像已读一样单独一张每人表 | 改动小，复用 #22 的权限检查；线程动作展开为对每封邮件的动作 |
| B | 新建会话表，归档、标签打在会话上 | 语义更像 Gmail，但迁移大，线程拆并时状态归属复杂，与交接封存要重新推 |
| 外部搜索引擎 | Meilisearch / OpenSearch | 多一套基础设施；项目只允许 PostgreSQL，不采用 |

## 5. 设计

### 5.1 位置

每封邮件恰好在一个位置，用 `placement` 字段表示：

| placement | 含义 | 界面显示 |
|---|---|---|
| `default` | 默认位置 | 收信在"收件箱"，发信在"已发送" |
| `archive` | 已归档 | 归档 |
| `folder` | 在自建文件夹，`folder_id` 指向它 | 该文件夹 |
| `trash` | 回收站，`trashed_at` 记录时间 | 回收站 |

- 移出回收站（恢复）回到 `default`。
- 回收站里的邮件 30 天后由 worker 永久删除（我的决定，与飞书和常见邮箱一致）。
- 现有 `DELETE /v1/mailboxes/:mailbox_id/messages/:message_id` 改为：不在回收站的邮件移进回收站；已在回收站的邮件永久删除。队列中尚未发出的邮件（#23 的 `queued`）被移进回收站时，和今天删除一样取消发送。
- 封存的历史（交接）不受影响，仍按现有规则排除在列表之外。

### 5.2 自建文件夹与标签

- 都属于邮箱，不属于个人。平铺，不嵌套。
- 名称在同一邮箱内唯一（忽略大小写），1–64 个字符；每个邮箱各最多 100 个（我的决定）。
- 标签有颜色，取自一组固定色板。
- 删除文件夹：其中的邮件回到 `default`。删除标签：从所有邮件上摘掉。

### 5.3 星标

- 新表 `mail_message_stars`，结构和现有 `mail_message_reads` 一样（成员 × 邮件），随成员和邮件级联删除。
- 列表、线程、详情里的 `starred` 都是当前查看者自己的。

### 5.4 权限（复用 #22 的 view / send / manage）

| 动作 | 需要的权限 |
|---|---|
| 阅读、标已读、加星标、搜索 | view |
| 移动位置（归档、移入文件夹、移进回收站、恢复）、贴/摘标签 | send |
| 永久删除（回收站里再删、清空回收站） | manage |
| 新建、改名、删除文件夹和标签 | manage |

前两行是共享状态会影响团队，所以要求 send；永久删除和改结构不可恢复或影响全员，所以要求 manage（我的决定）。个人邮箱只有本人，等同 manage。现有"删除需要 send"的规则不变（它现在变成移进回收站）。

这里的 manage 指**邮箱成员中的 manage 角色**（个人邮箱指本人），不包括组织所有者和管理员身上的 `manage_members`。#22 规定所有者和管理员不是成员就读不到邮件，所以他们也不能清空回收站或删改文件夹、标签，否则会永久删除自己看不到的邮件（我的决定）。访问对象需要新增一个表示"可整理结构"的标志。

### 5.5 会话线程

- 新增 `references` 字段，收信时从 `References` 头保存；回复时发出的邮件也带上 `In-Reply-To` 和完整的 `References` 链（被回复邮件的 `References` 加上它自己的 `Message-ID`；今天只放了一个 ID）。
- **线程两个方向都通（已确认）**：发信时由 Zmail 自己生成 RFC `Message-ID`（`<随机串@发信域名>`），在邮件入库排队前就写进新字段 `rfc_message_id`，随邮件头发给 Cloudflare。服务商回报的 ID 继续存在现有的 `message_id` 字段里，投递回执的匹配逻辑不变。#23 队列里稍后发出、防重重放的邮件都用入库时生成的同一个 ID。收信时把对方的 `Message-ID` 也存进 `rfc_message_id`，线程查找只看这个字段。
- 风险：Cloudflare 可能改写自定义的 `Message-ID`。实现第一步要先确认。做法是在测试环境向自己控制的收件箱发一封，看收到的邮件头，这一步由你执行或批准。如果会被改写，就改为在发信成功后保存 Cloudflare 回报的头值，未确认前线程按自定义 ID 工作。
- 以前已经发出的邮件没有 `rfc_message_id`，客户对这些旧邮件的回信仍会单独成线程，不做回填。
- 新增 `thread_id`：入库时在同一邮箱里找 `rfc_message_id` 出现在本邮件 `In-Reply-To` 或 `References` 中的邮件，找到就沿用它的 `thread_id`；找不到就用自己的 id 开新线程。
- **不按主题合并**，避免把"回复：会议"之类的邮件错并。
- 迁移时为已有邮件按 `in_reply_to` 回填 `thread_id`，按 id 顺序处理。
- 列表在某个位置里按线程聚合：一行一个线程，显示最新一封、线程内的邮件数、有没有我未读的、有没有我加星的。
- 打开线程显示它在该邮箱里所有不在回收站的邮件（不论位置），按时间排列。所以收件箱里的线程也能看到"已发送"里的回复。
- 对一行做动作（归档、标签、已读、移进回收站），作用于该线程在当前位置里的所有邮件。

### 5.6 搜索

- PostgreSQL 自带的全文搜索不切中文词，`zhparser` 托管数据库大多不支持，所以用 `pg_trgm` 三元组索引做子串匹配（`ILIKE`）。
- 对主题、发件人地址和名字、收件人和抄送、纯文本正文分别建 GIN trigram 索引。
- 关键词 3 个字符以上走索引；1–2 个字符在该邮箱范围内扫描（单邮箱的量级可接受）。
- 搜索范围：当前邮箱除回收站以外的所有位置；可叠加筛选：未读、星标、标签、有附件。
- 搜索结果按邮件列出，不聚合线程，按时间倒序。
- 迁移里 `CREATE EXTENSION IF NOT EXISTS pg_trgm`；PostgreSQL 13 起它是可信扩展，普通库主就能装。

### 5.7 计数与现有接口的行为

- 侧栏显示每个位置、文件夹的未读数（按当前查看者的已读状态），以及"星标"数。
- 邮箱上的 `unread_count` 改为只算收件箱（`default` 位置的收信）里我未读的（我的决定，和侧栏一致）。
- 列表不带 `placement` 时返回除回收站以外的全部邮件。今天删除后邮件就从列表消失，这样老客户端看到的行为不变（我的决定）。
- 组织级日志 `GET /v1/mail-messages`、统计、`GET /v1/outbound-mail-messages/:id` 不受位置影响：它们是投递记录，不是信箱视图（我的决定）。永久删除后的邮件和今天一样从这些接口消失。

### 5.8 哪些视图按线程聚合

- 只有位置视图（收件箱、已发送、归档、自建文件夹）按线程聚合；行动作作用于该线程在当前位置的全部邮件。
- 星标、标签、未读/附件筛选、搜索结果、回收站都按单封邮件列出；行动作只作用于那一封（我的决定）。

### 5.9 规模目标

- 按单个公共邮箱 20 万封邮件压测：线程列表首页 p95 < 200 ms，3 字符以上的搜索 p95 < 500 ms（我的决定）。
- 1–2 字符搜索做语句超时（2 秒），超时返回明确错误提示"请输入更长的关键词"，不拖垮数据库。

### 5.10 接口（细节由契约文件定）

- 列表 `GET /v1/mailboxes/:id/messages`：新增查询参数 `placement`、`folder_id`、`label_id`、`starred`、`unread`、`has_attachments`、`q`、`group=thread`；保留 `direction`，保持向后兼容。
- 单封更新 `PUT /v1/mailboxes/:id/messages/:message_id`：在 `read` 之外接受 `starred`、`placement`、`folder_id`、`label_ids`。
- 批量更新：新增一个接口，一次最多 100 封，同样的字段；按线程操作由前端展开成邮件 id。
- 线程：新增按 `thread_id` 取整段邮件的接口。
- 文件夹、标签：各一组增删改查接口；侧栏计数一个接口。
- 回收站：清空接口。
- Web BFF 和 Admin 只按 HTTP 契约对接；契约同步更新 `contracts/openapi.yaml` 和 `contracts/MAILBOXES.md`。
