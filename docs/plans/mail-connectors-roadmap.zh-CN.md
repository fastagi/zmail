# 统一收件与第三方邮箱接入：迭代计划与路线图

2026 年 11 月 21 日 · 草案，待产品评审
上级需求：[产品需求文档](../PRODUCT_REQUIREMENTS.zh-CN.md) R2（外部邮箱绑定与统一收件）、R4（AI 收件与 Agent），以及[邮箱权限功能需求](../MAILBOX_ACCESS_PRD.zh-CN.md)。
技术底座：[mail-connectors.plan.md](mail-connectors.plan.md)（切片 1 已完成，分支 `feat/mail-connectors`）。
原型与图示：`docs/design/v2/Connectors.blueprint.html`（五个可点击界面、架构图、绑定时序）。

## 1. 结论

1. **把"邮箱从哪来"和"谁能用"拆成两个独立维度。** 现在的 `external` 类型把"来自 Gmail"和"只有本人可读"绑在了一起。企业场景里，共享的 support@ 也可能托管在 Google Workspace 上。改为：访问方式（私人或共享）沿用现有权限模型不变，再加一个来源（自建或接入）。之后所有权限、交接、审计、AI 授权规则只认访问方式，与来源无关。
2. **接入方式分三种，对应三类人：**
   - 员工授权自己的账号（个人接入）
   - 管理员授权一个团队账号（共享接入）
   - IT 授权整个企业租户，再批量分配（租户接入）

   这正好接上现有业务：老板建组织、分配邮箱、分配员工。
3. **管理员管"连接"，不读"信"。** 这条和现有规则一致：组织管理员能看到、停用、交接连接，但不因角色自动读信。个人接入的账号属于员工本人，员工离开时只断开、不交接。
4. **Agent 只通过"授权"取信，不走组织 webhook。** 授权挂在邮箱上，由能管这个邮箱的人发放；与来源无关。所有来源都从同一个入库步骤进入 Agent 收件流（切片 1 已就位）。

## 3. 核心模型：访问方式 × 来源 × 接入方式

### 3.1 两个维度

| | 自建（Zmail 域名） | 接入（Gmail、Outlook、IMAP…） |
|---|---|---|
| **私人** | 现有私人邮箱：主人能读能发 | 员工自己的外部账号：主人只读（以后可选"以原地址回复"） |
| **共享** | 现有共享邮箱：成员按"查看/回复/管理成员"使用 | 团队在外部服务上的账号（如 Workspace 上的 support@）：成员按同样三级权限使用 |

数据上，`mailboxes.type` 回到 `personal | shared` 两个值，新增 `mailboxes.origin`（`zmail | connected`）。连接记录 `external_mail_connections` 仍然一个邮箱一条。产品还没正式上线，现有 `external` 行可以一次性迁移为 `personal + connected`。

### 3.2 三种接入方式

| 接入方式 | 谁发起 | 授权的是谁的账号 | 产生的邮箱 | 典型场景 |
|---|---|---|---|---|
| 个人接入 | 任何成员，为自己 | 员工本人的 Gmail 或 Outlook | 私人 + 接入 | 运营把自己注册平台用的 Gmail 接进来，统一查新信 |
| 共享接入 | 组织管理员 | 团队账号（以该账号身份登录授权） | 共享 + 接入，管理员分配成员 | 客服共用的 support@acme.com 托管在 Workspace |
| 租户接入 | 组织所有者 | 企业 Google Workspace（域级委派）或 Microsoft 365（应用权限），一次授权 | 管理员从目录里选择邮箱，逐个分配为私人或共享 | IT 给 100 名员工开通统一收件 |

租户接入最贴合现在的企业业务：老板建组织、IT 一次授权、像今天分配自建邮箱一样分配员工。但它的权限最大（技术上能读全租户），所以放在后面，且必须满足 §4 的约束。

## 4. 与现有角色的适配

### 4.1 权限矩阵

"读"指看信件列表和正文；"连接"指绑定、重连、解绑、看同步状态。

| 角色 | 个人接入（他人的） | 个人接入（自己的） | 共享接入 | 租户接入 |
|---|---|---|---|---|
| 组织所有者 | 不读；可在管理后台看到连接存在并强制断开（离职、风控） | 读；连接 | 不自动读，需像自建共享邮箱一样先把自己加为成员（留痕）；可绑定、分配、断开 | 唯一能授权和撤销租户的人；不自动读任何邮箱 |
| 组织管理员 | 同上 | 读；连接 | 同上 | 能从目录分配邮箱，不能授权或撤销租户 |
| 成员 | 无（看不到） | 读；连接 | 按被授予的查看、回复、管理成员 | 只用分配给自己的邮箱 |
| 共享邮箱"管理成员" | — | — | 增删成员；可重连 | — |
| Agent | 仅主人授权后 | 仅本人授权后 | 仅"管理成员"或管理员授权后 | 不能获得租户级授权，只能拿到具体邮箱的授权 |

### 4.2 关键规则

1. **读信权只来自访问方式**，与来源无关。现有全部入口（列表、搜索、统计、未读数、附件、API key、webhook）自动覆盖接入邮箱，不另开口子。
2. **组织 webhook**：私人接入永不推送；共享接入和自建共享一样，默认关，由"管理成员"开启。
3. **发送额度与邮箱上限**：接入邮箱不占组织 50 个自建邮箱的名额，另设"每人 10 个个人接入"和"每组织 N 个共享、租户接入"（N 随套餐）；只读阶段不消耗发送额度。
4. **邮件角色**（品牌身份分组）可以包含接入邮箱，例如"设计编辑部"角色下既有自建地址，也有编辑部的 Gmail。角色仍然只用于分组和显示，不授予权限。
5. **平台账号台账**的"注册邮箱"可以指向接入邮箱，满足 R3 的"平台 → 账号 → 注册邮箱"查询。可见范围按邮箱权限判断。

### 4.3 离职与交接

| 邮箱 | 员工离开时 | 交接 |
|---|---|---|
| 自建私人 | 进入"待交接"，历史封存（现行规则） | 管理员指定接手人 |
| 个人接入 | **立即断开**：退还授权、清除令牌、停止同步（本轮已实现）；已同步的副本无人可读 | 不交接，账号是员工本人的。副本按保留期删除（见 §8 决定 3）；员工重新加入并重绑时恢复原邮箱 |
| 共享接入 | 只失去成员资格（现行规则） | 不需要；连接属于组织 |
| 租户接入中分配给他的私人邮箱 | 与自建私人相同：待交接并封存 | 管理员指定接手人；也可以在租户侧直接停用该账号 |

## 5. 交互设计

### 5.1 员工：接入我的邮箱

1. **入口**：统一收件箱侧栏"邮箱"分组下方的"＋ 接入外部邮箱"，以及"设置 → 已接入的邮箱"。只显示实例启用的服务商（读 `GET /v1/external-mail-connectors`），每个服务商一个按钮。
2. **授权前说明**：一个小对话框写清楚三件事：只读；首次同步最近 14 天（可选 1–90 天）；管理员看不到你的信，你离开组织时连接会自动断开。确认后跳转到服务商授权页。
3. **回调页** `/console/mailboxes/connected/callback`：显示"正在完成接入…"，然后调用完成接口：
   - 201：跳回收件箱，打开新邮箱，顶部提示"已接入，正在同步最近 14 天的邮件"；
   - 200：提示"已重新连接"；
   - 409 或 422：用人话说明原因，并给"换一个账号"按钮。
4. **侧栏分组**：
   - "团队邮箱"：自建和共享接入；
   - "我接入的"：个人接入，带服务商图标和状态点。状态点绿色表示正常；黄色表示需要重新连接，并显示"重新连接"按钮；灰色表示已断开。
5. **统一收件箱**：每封信标来源徽标（已有）。筛选器增加"来源"（全部、Zmail、Gmail、Outlook…）。外部邮箱只读期间，阅读栏的"回复"换成"在 Gmail 中打开"深链，不让人误以为能从 Zmail 回。
6. **需要重新连接**：除状态点外，在收件箱顶部给一条一次性提示："你的 Gmail 授权已失效，最近一次同步在 3 小时前"，带"重新连接"按钮。
7. **解绑**：在设置里，二次确认文案写明"停止同步；已同步的 N 封信将在 30 天后删除，可立即删除"（以 §8 决定 3 为准）。

### 5.2 管理员：组织的连接

在现有组织管理后台（`/console/admin`）新增"外部连接"页：

- **列表**：员工、服务商、状态、最近同步、创建时间。个人接入的地址默认部分遮罩（如 `st***@gmail.com`），见 §8 决定 1。没有任何信件内容和数量。
- **操作**：
  - 强制断开（离职、风控），写入变更历史；
  - 共享接入："以团队账号授权"，然后走与"新建共享邮箱"相同的成员分配对话框；
  - 租户接入（所有者）：选择 Google Workspace 或 Microsoft 365，按向导完成管理员同意，再从目录中多选邮箱，逐行选择"分配给某员工（私人）"或"共享给某些成员"，逐行显示结果，支持重试。这复用公共邮箱管理一期的批量导入体验。
- **自建与接入在同一个"邮箱"总表里**，用"来源"列区分，便于 IT 一眼看到全部业务地址。

### 5.3 Agent：把收件交给 Agent

1. 在邮箱的"权限"面板新增"Agent"页签。有权发放的人（私人邮箱的主人、共享邮箱的"管理成员"）点击"授权一个 Agent"。
2. 授权时选择：
   - 哪个 Agent（API key 身份）；
   - 范围：整个邮箱，或按发件人、标签过滤；
   - 能力："读新信"，可选"起草回复"；
   - 有效期：默认 30 天，最长 90 天。
3. 授权后，Agent 通过收件流（游标拉取，或签名推送）拿到新信。每次读取和起草都记录"哪个授权、哪封信"，主人在同一页签可以看到最近活动并一键撤销。
4. Agent 起草的回复进入"待审"，由有"回复"权限的人确认后才发送。发送权始终在人手里。

## 6. 和现有业务怎么区分

| 维度 | 自建邮箱（现有业务） | 接入邮箱（新业务） |
|---|---|---|
| 地址归属 | 组织的域名 | 服务商或员工本人 |
| 开通 | 管理员新建并分配 | 个人自助；共享和租户由管理员或所有者 |
| 收信 | Cloudflare 投递，实时 | 同步，2 分钟一次（后续可接推送） |
| 发信 | Zmail 发送，占组织额度 | 只读；以后"以原地址回复"走服务商，单独授权和审计 |
| 计费名额 | 组织 50 个自建邮箱 | 每人 10 个个人接入；共享和租户接入按套餐另计 |
| 离职 | 待交接、封存 | 个人接入：断开，不交接；共享接入：同自建共享 |
| 统一收件、搜索、AI 分流、Agent | 同一套 | 同一套（入库后完全一致） |

**一句话：入库之前各走各的路，入库之后完全一样。** 这条界线也是代码的界线：服务商差异只在连接器文件里，入库之后的全部规则共享。

## 7. 迭代计划

每个迭代都要能独立上线、独立验收。时长按一名全栈开发者估算，含测试与评审。

| 迭代 | 内容 | 验收 | 依赖 | 估时 |
|---|---|---|---|---|
| **C0 底座**（已完成） | 连接器注册表、绑定和重连、统一入库、投递隔离、离职断开 | 自动化测试 + 本地实测（§2） | 无 | — |
| **C1 模型与可见性** | `origin` 维度迁移（`external` → `personal + connected`）；侧栏和列表按 §8 决定 1 隐藏他人的个人接入；管理后台"外部连接"列表与强制断开；变更历史记录绑定、断开、离职断开 | 越权回归：他人、管理员、离职后从列表、搜索、统计、未读数、API 任何入口都看不到个人接入的内容和地址 | 决定 1、2 | 1 周 |
| **C2 Gmail 与 Outlook 个人接入** | 先补 §11 的适配器接口缺口；两个真实适配器：Gmail history 增量、Outlook 按文件夹 delta、令牌刷新与轮换、限流退避、HTML、附件元数据、回填天数；支持组织自带 OAuth 应用（§12 结论 8）；Web 授权对话框、回调页、"我接入的"分组、状态点、重连提示、"在 Gmail 中打开" | 一名运营在一页看到自建、Gmail、Outlook 各一封真实新信；重连、重复通知不多出副本；撤权后停止同步 | Google、Microsoft OAuth 应用（§9）；适配器代码可先写，用模拟服务端测试 | 2–3 周 |
| **C3 共享接入** | 管理员以团队账号授权，创建"共享 + 接入"邮箱并分配成员；webhook 开关沿用；共享接入的重连由"管理成员"完成 | 两名员工共同处理托管在 Workspace 的 support@，各自已读；无权成员任何入口看不到 | C1、C2 | 1 周 |
| **D1 Agent 授权与收件流** | 授权模型（§5.3），游标拉取接口和签名推送，每次读取审计，Web "Agent"页签 | PRD R4 验收："小王 × 平台 A"任务读不到无关历史；撤权后立即停止；仅创建模板的密钥不能读信 | 决定 4、5 | 2 周 |
| **D2 Agent 任务** | 分流 → 待办 → 起草 → 人工确认 → 发送；同一封邀请只生成一条待办 | 用真实一周来信校正误报和漏报 | D1、AI 服务商 | 2 周 |
| **C4 租户接入** | Workspace 域级委派、M365 应用权限；目录读取、批量分配、逐行结果；离职走自建私人的交接规则 | 100 个地址试点可对账、可逐行重试；IT 撤销租户授权后全部停止 | C1、C3；企业客户的管理员同意 | 3 周 |
| **C5 IMAP 连接器** | 通用 IMAP（iCloud、Yahoo、QQ、163、自建服务器），使用应用专用密码，加密保存 | 用三个不同服务商各收一封信 | 决定 6（引入依赖） | 1–2 周 |
| **C6 以原地址回复** | Gmail send、Graph sendMail、SMTP；单独的"代发"授权；发出的信回写为已发并入线程 | 未授予代发不能发；代发全部审计 | C2；服务商发送权限审核 | 2 周 |

### 7.1 路线图

| 时间（目标） | 交付 | 对外可用的样子 |
|---|---|---|
| 第 1–2 周 | C1 + C2 代码（模拟服务端） | 内部演示：用测试账号接入 Gmail 和 Outlook |
| 第 3 周 | OAuth 应用就绪后发布 C2 | 试点：运营在一页看三种来源 |
| 第 4 周 | C3 | 团队共同处理托管在 Workspace 的共享邮箱 |
| 第 5–6 周 | D1 | Agent 在授权范围内读新信 |
| 第 7–8 周 | D2 | AI 待办和起草，人工确认后发送 |
| 第 9–11 周 | C4 | 企业 IT 一次授权、批量开通 |
| 之后 | C5、C6、C7 | 更多服务商、以原地址回复、近实时 |

**最长的外部等待是 Google 的受限权限审核**：`gmail.readonly` 需要验证加每年一次的 CASA 安全评估，评估费 500 到 4,500 美元，整体要数周。应在第 1 周就提交，与 C1、C2 开发并行。

审核通过前的两条路：

- "测试用户"模式：最多 100 人，但授权（含刷新令牌）**同意后 7 天过期**，试点用户每周要重连一次。只适合内部演示。
- **组织自带 OAuth 应用**：Google 对"内部使用"的应用免审核。企业试点客户在自己的 Workspace 里建一个内部应用，把客户端 ID 和密钥填进 Zmail，就不受我们公共应用审核进度的影响。建议作为企业试点的默认路径。

| 1 | 管理员在邮箱列表里能否看到员工个人接入的地址 | 不能。只在"外部连接"页看到遮罩地址和状态，用于离职与风控。理由：个人 Gmail 地址本身就是私人信息，现行"管理员看到所有地址"的规则是为组织自有地址设计的 |
| 2 | 是否做 `origin` 维度迁移（§3.1） | 做，且在 C1 做。产品尚未正式上线，迁移成本最低；不做的话共享接入（C3）和租户接入（C4）都要另造规则 |
| 3 | 解绑或离职后，个人接入的副本保留多久 | 30 天后自动删除，员工可立即删除；保留期内员工重新加入并重绑可恢复 |
| 4 | Agent 能否看到明文验证码 | 默认遮罩；授权时可以由主人显式勾选"允许读取验证码"，并单独审计 |
| 5 | Agent 的身份 | 先用"某个人的 API key + Agent 标记"，权限上限不超过这个人；企业级"组织拥有的 Agent"放到 C4 之后 |
| 6 | 是否引入 IMAP 依赖库 | 同意引入一个维护良好的库，按 DEPENDENCY_SECURITY.md 评审；它能一次覆盖大量没有 OAuth 的服务商 |
| 7 | 首批试点支持的账户类型 | 个人 Gmail + Google Workspace（个人接入）、Microsoft 365；个人 Outlook.com 随后 |

- 本地开发环境实测（假连接器）：服务商列表；发起和完成绑定；state 重放被拒；重连换号被拒；同号重连恢复；未知服务商被拒；解绑；解绑后重绑复用原邮箱；同事绑定的账号被拒；组织所有者读同事外部邮箱被拒；组织所有者替同事开启 AI 分流被拒；签名投递到外部地址返回 404；移除成员后其连接被撤销、令牌清除；同步 worker 只处理有效连接并记录游标。

## 11. 复查切片 1 后要补的接口缺口

写真实适配器之前，`ExternalMailSource` 这层接口需要先改。全部在 C2 的第一步完成。

| 缺口 | 现状 | 改法 |
|---|---|---|
| 令牌轮换 | `Fetch` 不返回新令牌 | `Fetch` 结果带可选的新刷新令牌，与同步结果在同一事务保存。Microsoft 会轮换刷新令牌，不存就会在下次同步失效 |
| 回填与增量混在一起 | 空游标即回填，一次调用返回全部 | 拆成两个任务：回填按页推进、进度落库、可续跑，从新到旧；增量只跑游标。结果带"还有更多"标记，有则立即再排一次 |
| 游标形状 | 一个文本字段 | Gmail 每账号一个 `historyId`；Graph 增量是每个文件夹一个 `deltaLink`；IMAP 是每文件夹的 UIDVALIDITY 和 UID。游标改为适配器自己编码的不透明 JSON |
| 游标过期 | 当作普通拉取失败 | 新增 `ErrExternalMailCursorExpired`：进入有上限的重新对齐（按回溯天数），靠 `external_id` 去重 |
| 远端状态变更 | 不处理 | 只同步新信、已发和删除标记；不同步已读（已读是每人各自的）、归档和标签。照 Front 的做法起步 |
| 附件 | 不同步 | 只存元数据，打开时经适配器按需取，带大小上限 |
| 限流 | 每连接 2 分钟一次 | 按服务商一个并发预算，按连接指数退避加抖动 |
| 运行记录 | 只有日志 | `external_mail_sync_runs` 表：每次同步一行（开始、结束、拉取数、入库数、错误码），供状态页和排障 |

本轮已顺手修复一处：已解绑的连接仍计入每人 10 个的上限，反复解绑后会无法再绑定。现在只计有效连接。

## 12. 后台长任务

全部跑在现有的 PostgreSQL 任务队列上，不引入新基础设施。每个任务都有租约、幂等键和明确的失败去向。

| 任务 | 触发 | 幂等 | 失败处理 | 状态 |
|---|---|---|---|---|
| 回填 | 绑定成功；游标过期 | `(mailbox_id, external_id)` 唯一；分页游标落库 | 退避重试，进度保留，界面显示"已同步 N 封" | 待做（C2） |
| 增量同步 | 每连接 2 分钟；或收到推送 | 同上；连接行上的租约 | 授权失败转"需重新连接"；其他错误下个周期重试 | 已有（轮询） |
| 推送订阅续期 | 到期前定时 | 每连接一条订阅记录 | 续期失败退回轮询，不丢信 | 待做（C7） |
| 令牌刷新 | 拉信前按需 | 新令牌与同步结果同事务保存 | 被拒转"需重新连接"并通知主人 | 待做（C2） |
| 副本清理 | 解绑或离职后到保留期 | 按邮箱分批删除，可重入 | 下次继续 | 待做（C1） |
| Agent 收件投递 | 新信入库时同事务写入待投递 | 每个授权一个单调游标；事件带稳定 ID | 重试后进死信；拉取端不受影响 | 待做（D1） |
| 租户目录同步 | 每天；管理员手动 | 按目录对象 ID 对账 | 只标记差异，不自动开通或回收 | 待做（C4） |

## 13. 竞品调研（2026-11-21）

依据各家公开文档；价格只取计费单位，具体数字各来源不一致，不作依据。

| 产品 | 接账号的方式 | 是否存信 | 新信到达 | 授权失效 |
|---|---|---|---|---|
| [Nylas v3](https://developer.nylas.com/docs/dev-guide/best-practices/grant-lifecycle.md) | 每邮箱一个 grant，托管 OAuth 或批量授权 | Gmail、Microsoft 直通不存；IMAP 缓存 90 天 | webhook；Gmail 实时需自建 Pub/Sub | grant 变 invalid；重新授权保留原 ID；失效超 72 小时的信不补推 |
| [Unipile](https://www.unipile.com/communication-api/email-api/) | 托管授权或自带 OAuth 应用；IMAP 自动探测 | 存在其服务器 | webhook | 未查到 |
| [EmailEngine](https://learn.emailengine.app/docs/accounts/gmail/gmail-api) | 必须自带 OAuth 应用（自托管） | 只存元数据，正文按需取 | Pub/Sub 或 IMAP IDLE；否则约 10 分钟轮询 | `authenticationError` 事件 |
| [Aurinko](https://docs.aurinko.io/llms-full.txt) | 个人、服务账号（组织级）、用户会话三种 | 不存正文 | 签名 webhook；增量令牌 | 生命周期事件 |
| [AgentMail](https://agentmail.to/docs/permissions) | 不接已有邮箱，只开新邮箱 | 存 | webhook 和 WebSocket | 不适用 |
| [Composio](https://docs.composio.dev/docs/subscribing-to-connection-expiry-events.md) | 每用户一个 connected account | 不存 | 轮询触发器转 webhook | 账号变 EXPIRED，触发器自动停用 |
| [Front](https://help.front.com/en/articles/205312) | 每邮箱 OAuth，分共享和个人 | 存；可导入最近 5 万封 | 持续同步新信、已发、垃圾状态 | 重新授权后补导入 |

服务商事实（官方文档）：

- Google：`gmail.readonly` 是受限权限，需验证加每年 CASA 评估；测试模式 100 人且授权 7 天过期；`users.watch` 至少每 7 天续一次，通知可能丢；`historyId` 过旧返回 404，需全量重新同步。内部使用和全域安装的应用免审核。
- Microsoft Graph：消息增量按文件夹；邮件订阅最长不到 7 天；应用权限必须管理员同意；"应用的 RBAC"可以把应用限制到指定邮箱，变更生效需 30 分钟到 2 小时。
- IMAP：Exchange Online 必须 XOAUTH2；iCloud 用应用专用密码。Yahoo、Fastmail、QQ、163 的做法只查到第三方来源，未核实。

**八条结论**

1. 我们必须存信：统一收件箱、搜索、AI 分流和 Agent 都需要本地有信。回填要有上限，从新到旧。
2. 连接是一等对象，重新授权原地恢复。已实现。
3. 推送只当提示，轮询兜底，订阅要续期。
4. 游标按服务商的形状存，过期时有上限地重新对齐。见 §11。
5. 远端状态只同步必要的。见 §11。
6. 给 Agent 的事件至少投递一次、带稳定 ID、可按游标重放；只靠 webhook 会丢。
7. Google 审核是最大的外部成本，且每年一次。
8. 企业客户可以绕开审核：自带内部应用，或租户接入。Microsoft 侧用"应用的 RBAC"限制到被分配的邮箱。

对计划的调整：C2 增加"组织自带 OAuth 应用"；C4 的 Microsoft 实现以"应用的 RBAC"为前提；D1 的权限模型照 AgentMail：按邮箱限定的密钥加能力白名单，发信一律先起草再由人确认。
