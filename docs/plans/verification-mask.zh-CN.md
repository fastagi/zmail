## 1. 要解决的问题

团队共享邮箱里会收到平台发来的验证码、登录链接和重置密码链接。今天这些内容原样出现在：

- 邮箱列表与统一收件的标题、摘要（`toMailMessageSummary` 的 `subject`，`InboxItemResponse.snippet`）；
- 邮件详情和线程（`toMailMessageResponse` 的 `text_body`、`html_body`）；
- 组织投递日志 `GET /v1/mail-messages`（`toMailLogEntries`）。这个日志给组织管理员看，管理员可能并不是该邮箱的成员。

结果是：路过屏幕的人、只想看投递记录的管理员，以及以后接入的 AI 分流（切片 ③），都能直接拿到秘密。

## 2. 目标、非目标、反目标

目标：

1. 来信（`direction = inbound`）中的验证码和敏感链接，在所有列表、日志、摘要和详情接口里默认被遮罩。
2. 有权阅读该邮箱的人在阅读栏点"显示验证码"，才拿到原文。每次显示都留下结构化日志 `mail.secret_revealed`。
3. 阅读栏显示原型里的锁定面板，列表摘要不暴露秘密。
4. 为切片 ③ 定下规则：任何送往 AI 的内容只能取遮罩后的版本。

非目标：

- 不改存储。数据库里仍是原文，遮罩只在输出时进行，所以没有迁移，也不需要回填。
- 不遮罩外发邮件。那是用户自己写的内容；事务邮件已有自己的遮罩（`transactional_mask.go`）。
- 不遮罩附件内容，不做 OCR。
- 不提供"永久显示 / 信任此发件人"。

反目标：

- 误伤日常内容：订单号、年份、日期、时间、金额、十六进制颜色、电话号码片段不能被当成验证码。
- 让 HTML 正文变形：遮罩后的 HTML 必须保持原有结构和样式，只替换命中的文字和链接。
- 只遮罩显示层：API 响应本身就必须不含秘密。只在前端藏起来不算。

## 3. 检测规则

检测器写在 `api/internal/modules/mailbox/secret_mask.go`，是纯函数，无依赖、无状态。

### 3.1 验证码

满足以下全部条件的词元会被替换为 `••••••`（沿用 `maskedSecret`）：

1. 形态，任选其一：
   - 4–8 位纯数字；
   - `3 位数字 + 空格或连字符 + 3 位数字`（如 `123 456`、`123-456`）；
   - 6–8 位字母数字混合，至少含一位数字和一位字母（如 `A7K9Q2`）。
2. 边界：两侧都不是字母或数字。紧邻的符号还要满足下列规则，否则视为更大结构的一部分，不算验证码：
   - 前一个字符是 `#`：十六进制颜色或编号。
   - 前一个字符是 `-`、`/`、`.`、`:`，且再往前是数字：日期、时间、版本号或小数。
   - 后一个字符是 `-`、`/`、`.`、`:`，且再往后是数字。
   - 前一个字符是 `¥`、`$`、`￥`、`€`、`£`：金额。
3. 上下文：词元前 40 个字符内，或后 20 个字符内，出现关键词（不区分大小写）：
   - 中文：验证码、校验码、动态码、确认码、登录码、安全码、激活码、口令、动态密码；
   - 英文：code、otp、passcode、pin、verification、verify、one-time、2fa、security code、login code。

   英文关键词按单词边界匹配，`pin` 不会命中 `shipping`。

设计决定（待确认）D1：只有带关键词上下文的数字才遮罩。宁可漏掉没有任何说明的裸数字，也不误伤订单号和金额。

### 3.2 敏感链接

满足以下条件的 http(s) 链接会被替换为 `主机名 + /••••`（沿用 `maskSecret` 的写法）：

- 链接的路径或查询串（不区分大小写）含下列任一片段：`reset`、`recover`、`verify`、`verification`、`confirm`、`magic`、`token`、`login`、`signin`、`sign-in`、`auth`、`otp`、`password`、`activate`。

纯文本中的链接按 `https?://` 开头、直到空白或 `<>"'` 结束来识别。HTML 中检查 `<a href>` 和文字两处。

设计决定（待确认）D2：`unsubscribe`、`invite` 不算敏感。退订链接需要能直接点；邀请链接不能单独用来接管账号。

### 3.3 HTML 正文

用 `golang.org/x/net/html` 的分词器逐个读取记号：

- 只在文本节点里找验证码。`<style>`、`<script>`、`<textarea>`、`<title>` 内的文本不处理，避免把 CSS 颜色当成验证码。
- 关键词上下文可以跨节点向前看。前一段文本的最后 40 个字符会作为本节点的前置上下文，所以 `<p>您的验证码：</p><p><b>123456</b></p>` 也能命中。
- 没被修改的记号原样写回（`Raw()`），只重写被修改的文本节点和 `href`。这样遮罩后的 HTML 与原文逐字节相同，命中处除外。

### 3.4 标题与摘要

- 标题按 3.1、3.2 处理。例如 "Your verification code is 482913" 输出为 "Your verification code is ••••••"。
- 摘要从正文前 400 个字符截取。先对这 400 个字符做遮罩再截短。

设计决定（待确认）D3：如果 400 个字符的截断正好切在一个数字串中间，就丢弃末尾那串不完整的数字或字母，免得露出半个验证码。

## 4. 接口

### 4.1 默认遮罩

以下输出对来信一律遮罩，出站信原样输出：

| 输出 | 字段 | 位置 |
|---|---|---|
| 邮箱列表、线程列表、搜索、统一收件 | `subject` | `toMailMessageSummary` |
| 统一收件 | `snippet` | `inbox_service` 的摘要来源 |
| 邮件详情、线程详情 | `subject`、`text_body`、`html_body` | `toMailMessageResponse` |
| 组织投递日志 | `subject` | 经 `toMailMessageSummary` |

详情新增字段 `secrets_masked`（布尔）：只要标题或正文里有内容被遮罩就为 `true`。这是对契约的增量修改。旧客户端会忽略它，照常看到遮罩后的文字。

设计决定（待确认）D4：列表项不加这个字段。前端判断"是否显示锁定面板"只看详情。列表标题本身已经是遮罩后的样子。

### 4.2 显示原文

`POST /v1/mailboxes/{mailbox_id}/messages/{message_id}/reveal`

- 只放在会话路由组里，API key 不能调用（API key 本来也没有读信路由）。
- 权限和 `GET .../messages/{message_id}` 相同：要求该邮箱的查看权限；需要查看历史时，规则也与详情一致。无权时返回 404，与详情一致，不暴露邮件是否存在。
- 返回 `MailMessageResponse` 的原文，`secrets_masked = false`。
- 用 POST 是因为它有副作用（会记日志），而且不应被缓存或预取。响应带 `Cache-Control: no-store`。
- 记录结构化日志：事件 `mail.secret_revealed`，字段 `user_id`、`mailbox_id`、`message_id`。不记录秘密本身。

设计决定（待确认）D5：本切片只写结构化日志，不新增审计表。邮箱权限模块的访问事件表记录的是成员变更，语义不同；以后要做通用审计时再迁移。

"管理员看不到"在本切片的含义：组织管理员通过投递日志只能看到遮罩后的标题。日志没有详情接口，也没有显示原文的入口。管理员如果本身就是该邮箱的成员，就与普通成员一样可以点显示。

### 4.3 对 AI 隐藏

现在没有 AI 调用，Webhook 载荷不含标题和正文（`webhook_events.go`）。本切片定下规则，写进 `api/internal/modules/mailbox/README` 或模块注释，供切片 ③ 遵守：送往 AI 的标题和正文必须取 `maskInboundSecrets` 的输出，不得调用显示原文的代码路径。

## 5. 界面

- 阅读栏（`InboxReadingPane` 及单邮箱阅读视图）：当详情 `secrets_masked` 为真时，在正文上方显示锁定面板，样式照原型：
  - 虚线边框、圆角 12、居中；
  - 第一行是 22px 的"● ● ● ● ● ●"；
  - 下方文案"验证码已隐藏。只有这个邮箱的成员能看，AI 和管理员看不到。"；
  - 按钮"显示验证码"。
- 点击按钮后经 BFF 路由调用显示原文接口，用返回的原文替换本次阅读的标题和正文。只保存在组件状态里，不写入查询缓存，换一封信再回来时重新遮罩。面板变成一行小字"已显示验证码"。
- 正文区仍显示遮罩后的正文，`••••••` 原样出现在文字中，用户能看到秘密原本在哪里。
- 列表摘要照接口原样显示，不做额外处理。

设计决定（待确认）D6：面板放在正文之上，不替换整个正文。邮件里其余内容（例如"如果不是你本人操作……"）照常可读。

## 6. 测试

- 检测器单测（表驱动）：
  - 中文、英文验证码；空格或连字符分隔的码；字母数字混合码；
  - 关键词在后的写法；跨 HTML 节点的写法；
  - 不误伤：年份、日期、时间、金额、`#a1b2c3`、订单号（无关键词）、`shipping 12345`、`<style>` 内的颜色；
  - 敏感链接只保留主机名，退订链接不动；
  - HTML 未命中时逐字节不变；
  - 摘要截断时丢弃不完整的尾部数字。
- 输出层单测：
  - 来信的列表、详情、日志都已遮罩，`secrets_masked` 为真；
  - 出站信不遮罩。
- 处理器测试：显示原文接口的权限与 404 规则、返回原文、`no-store`、日志事件。
- 路由目录与契约：更新 `contracts/openapi.yaml`、`contracts/MAILBOXES.md`，并重新生成 web 与 admin 的类型。
- kest 验收流：用 log 服务商在 `test.zmail.im` 投入一封带验证码的模拟来信，确认详情已遮罩，显示原文接口返回原文。
- Web 组件测试：锁定面板的显示与点击、BFF 路由；1440×900 浅色、深色各截图一次。

## 7. 发布与回退

- 无迁移，无配置开关。部署后所有来信立即生效。
- 回退：换回旧镜像即可。旧前端忽略 `secrets_masked`，旧后端不遮罩。
- 风险：误伤会让正常数字变成 `••••••`。用户可以点显示原文看到原文，所以不会丢信息。
