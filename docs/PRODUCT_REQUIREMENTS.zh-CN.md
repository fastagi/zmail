# Zmail 产品需求文档

2026 年 11 月 18 日 · v1.0 · 产品评审稿
产品入口：[zmail.im](https://zmail.im)。适用对象为产品、设计、研发、运营和企业 IT。下文的发布顺序和试点目标是建议，尚未排期。

## 1. 产品要解决的问题

一名运营可能同时代表工作室、设计编辑部和教程栏目，在多个平台拥有账号，还要用团队邮箱给不同订阅名单发消息。今天，邮箱、平台主页、账号负责人和客户回复分散在不同地方。交接时很难回答“这个账号用哪个邮箱注册”“这封邀约今天要不要回”。员工自己的验证码和私人邮件又不能因为集中管理而对全组织可见。

**愿景**是让一个人也能管好大量业务邮箱和平台账号，让团队用自己的品牌与客户沟通，让 AI 在明确授权下先读信，把值得处理的事交给对的人。客户保有域名和身份，收件人可以退订，所有发送、读取和自动操作都能解释来源与结果。

## 2. 谁在什么情况下使用

| 使用者 | 典型任务 | 完成的标志 |
|---|---|---|
| 媒体运营 | 维护不同角色的平台注册邮箱，早上查新信，给编辑部订阅者发周报 | 能从平台找到对应角色、邮箱、负责人和待办；可追溯到原信 |
| 企业 IT | 为 100 名员工或受管业务账号批量分配地址、移交账号、回收离职权限 | 每行开通结果可查；管理员可以管理归属，员工仅能阅读获授权的邮件 |
| 员工与协作团队 | 员工使用私人邮箱；客服、编辑或 IT 共同处理共享邮箱 | 用各自的账号登录，能看到自己的信及获授权的共享信箱 |
| 营销负责人 | 导入名单、试发、排期、追踪失败、仅补发给遗漏收件人 | 每位收件人都有可解释的结果，重试不重复发送 |
| 受托 Agent | 创建品牌模板，读取获授权的新信，辅助账号开通 | 每个操作可归到任务、授权人和邮箱，人员可复核和撤权 |

## 4. 功能需求与验收

### R1 · 域名、地址和邮箱权限

- 支持组织验证自有域名、创建简短邮箱、批量开通、查重、查看路由是否可用。需要独立会话和权限时开独立邮箱；仅需区分平台来信时可建别名，须保留原始收件地址。有些平台拒绝加号地址，应支持独立命名。
- 产品规模目标是一个人能持续增加和管理地址。控制台应分别显示可用地址、邮箱、路由及厂商额度。先验收 100 个地址并可逐行重试，再以万级地址测试检索和费用；“无限量”不作容量承诺。
- 私人邮箱默认本人可读。共享邮箱可分别授予查看、用该地址回复、管理成员三种权限。运维负责开通、停用和交接；管理组织本身不自动授予私人正文阅读权。
- 邮箱权限、离职交接和每人已读的详细规则见 [邮箱权限功能需求文档](MAILBOX_ACCESS_PRD.zh-CN.md)。产品尚未正式上线，不做迁移预览；现有邮箱上线时一次性转为共享邮箱。
- **验收**：导入含重复项的 100 行后能对账，不重复创建。两名员工交叉测试列表、未读数、全局搜索、正文、附件、历史链接、API、事件和 AI 通知；无权限方不能借任一入口获取信件。

### R2 · 外部邮箱绑定与每日统一收件

- 在邮箱页提供「绑定 Gmail」「绑定 Outlook」。所有者通过官方 OAuth 登录并选择账号，可绑定多个。先支持只读，再按需授权用原地址回复。私人邮箱默认仅绑定人可见，团队协作和 AI 阅读分别授权。
- 统一收件箱同时展示自建、Gmail 和 Outlook 来源，按收件时间排序，标明收件地址、角色和来源。提供今日新到、未读、待处理及按邮箱筛选；邮箱新增记录单列，避免把未读旧信当作今日新信。
- 展示最后同步时间、异常原因、重连和解绑入口。解绑立即停止拉取与代发；绑定前说明历史同步范围和解绑后的历史保留规则。服务商审核、企业管理员授权以及邮箱类型支持范围须在试点前校验。
- **验收**：同一运营在一页看到三个来源各一封真实新信，重连或重复通知不会多出副本；未授予发送权不能代发。撤权后停止同步，其他员工通过搜索也看不到私人主题。

### R3 · 角色、平台账号与员工开通任务

- 角色台账记录品牌身份、负责人、发件邮箱和内容定位。外部平台账号记录平台、主页、角色、注册地址、状态及交接历史。一个角色可有多个地址，一个地址也可关联多个平台。
- 支持搜索“平台 → 账号 → 注册邮箱”和“地址 → 角色 → 名下账号”，并区分邀请已到、等待员工确认、开通成功、超时和待复核。邮件送达不直接判定注册成功。
- 创建员工开通任务时指定人、平台、邮箱、负责人和授权时限。企业平台已有受管理账号或官方邀请流程时优先衔接，例如为公司 Mac 分配员工账号。设备管理与社交媒体内容发布属于各平台自身能力；在 Zmail 中记录账号不意味着可以跨平台发帖。
- **验收**：以设计编辑部为例，从一次平台注册邀请定位到该角色，完成确认后能追溯证据；负责人离职后，新负责人接手业务账号，原负责人失去业务邮箱权限。

### R4 · AI 收件、通知和模板接口

- 托管业务邮箱可设置“新信先由 AI 分流”；私人邮箱须由本人授权。Agent 有独立身份，可授予指定邮箱、任务、有效期和动作。到期或撤权后停止读信。
- 欢迎信和常规通知归档并纳入摘要；合作邀约、审核、续费提醒生成待办，附原因、负责人、期限和原信；异常登录、扣款失败等按策略及时通知。来源或归属不明确时进入人工复核。运营可改判、静音并追查通知历史。
- 验证码、恢复链接和正文按原信权限保护，通知列表不暴露秘密。来信正文作为待分析数据，不凭邮件里的指令扩大访问、代发、付款或改变账号归属。
- 模板接口允许 AI 新增可复用主题、HTML/纯文本和示例变量。创建、阅读收件和实际发送使用独立权限。运营能在网页预览、编辑，决定是否发送。
- **验收**：同一邀请重复投递只生成一条待办；给 Agent 一条“小王 × 平台 A”任务，读不到小王无关历史或平台 B 的验证邮件。仅创建模板的密钥可以保存模板，不能群发。

### R5 · 营销群发与批量业务通知

- 订阅周报、活动邀请按名单群发；入场、改期、截稿等通知按参与者或业务名单发送。运营先创建分组再导入 CSV，看到新增、更新、跳过和错误原因。同一联系人可属多组，重复导入保留退订与抑制状态。
- 从角色选发件身份、模板和名单，预览变量、人数和收件范围。支持单人试发、小批试发、立即或定时发送、暂停、恢复与取消。普通成员准备草稿，具备发送权限者启动。营销用途明确展示退订入口。
- 补发应能选择遗漏对象，预览与原批次的重叠。现有做法是另建名单；后续提供按历史批次排除已发者。按联系人固定批次受众，实际发送前复查退订和永久退信状态。
- **验收**：用同一周报先发 1 人，再为新增的 3 人补发。四人各收到一封，首位收件人不会重复收到。超额度时说明排队原因，额度恢复后继续；结果未知的发送不盲目换厂商重试。

### R6 · 队列、回执与可追溯历史

| 运营问题 | 产品口径 |
|---|---|
| 这批处理了多少？ | 队列进度＝（总人数－待处理人数）÷总人数。跳过、取消和失败都已处理。 |
| 尝试过的发送中成功多少？ | 发送成功率＝已发÷（已发＋失败）。尚未尝试时显示“—”。跳过、取消不进入分母。 |
| 对方服务器收到了吗？ | 展示提供商接受、已投递、退信和投诉等实际事件，保留时间及关联邮件。未取得回执明确标记未知；已投递不代表进入主收件箱或已读。 |
| 某个人收到哪一封？ | 从广播下钻到收件人、邮件详情和事件历史，可按邮箱、时间、批次及状态查询。 |

**验收算例**：10,000 人中已发 7,920、失败 80、待处理 2,000 时，同时显示队列进度 80% 和发送成功率 99%。用模拟或专用测试环境验证大批次；真实上线规模受组织和厂商额度共同约束。

### R7 · 品牌身份与发信厂商

- 官网提供客户配置入口。官方产品通知、共享试用和客户正式业务使用可辨识的发件身份；支持自有域名、品牌模板、回复地址、SPF/DKIM/DMARC 检查和投递反馈。品牌头像后置。
- 保留 Cloudflare，增加按组织绑定发信厂商的能力，支持厂商 API 和通用 SMTP。凭据仅放在服务端，显示测试结果、可用能力和额度；切换后历史记录、退订与投诉处理仍有效。
- 与 Gmail/Outlook 绑定分别建模。前者决定业务邮件通过哪家服务投递，后者决定某个已有邮箱的哪些邮件可同步、是否可代表本人回复。
- **验收**：同一品牌身份通过两个已授权厂商分别完成测试，记录实际使用的厂商及可取得的回执。只支持提交回执的连接不能显示“已投递”。

## 5. 交付顺序与运营指标

| 建议阶段 | 交付与放行条件 |
|---|---|
| A · 巩固现网 | 保留周报、收发和补发回归样例；发布 AI 创建模板 API，并在 docs/testing/ACCEPTANCE_TEST_PLAN.md 增加用例：仅含 templates:create 的密钥能保存模板，调用发送或广播接口被拒绝。运营人员用独立账号；生产自助注册关闭，须先明确由谁、以何种方式开通这些账号。补齐 zgi.app 多地址收信的实测记录。 |
| B · 邮箱权限与规模 | 先完成邮箱权限隔离、每人已读和离职交接，再开放批量短地址和别名。通过双员工越权回归、离职交接和 100 地址试点。 |
| C · 统一收件 | Gmail、Outlook 分别完成只读绑定、同步、重连、撤权和来源显示。代发单独验收。 |
| D · 角色运营与 AI | 上线账号台账、范围受限的读信授权、待办与通知。运营用真实的一周来信校正误报和漏报。 |
| 并行 · 多厂商 | 用试点客户现有的第二厂商验证接入成本、回执和故障恢复，再扩展厂商数量。 |

试点同时观察三种使用习惯：每周完成真实客户邮件往来的组织数、完成批量通知的组织数、通过 AI 待办处理实际事项的运营人数。记录首次绑定到首封新信的耗时、同步延迟、人工每日查信耗时、关键事项漏报、通知误报、永久退信和投诉。先采集基线再定目标。权限越界和由重试导致的重复群发，在验收样例中都要求为零。

## 6. 待产品评审的决定

1. 首批客户优先验证媒体运营多账号、员工开通还是客户通知？建议三类分别统计，并用实际使用频率决定投入。
2. Gmail 和 Outlook 试点支持哪些个人和企业账户？首次回溯多久，解绑后何时清理副本，员工离职如何交接共享数据？
3. 首个商用套餐提供多少独立邮箱、别名和发送额度？厂商费用由谁承担？不把额度扩大等同于无限投递。
4. 哪些通知即时发送、哪些进入每日摘要？默认送达 Zmail 待办，其他通知渠道和响应时限定在试点中确认。
5. 哪些业务通知允许发送、如何记录同意或其他依据，以及退订适用于哪个品牌和用途？规则确定前沿用当前订阅与抑制约束。
