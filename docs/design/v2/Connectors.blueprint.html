思路

入库之前各走各的路，入库之后完全一样

企业今天在 Zmail 里做三件事：老板创建组织，管理员分配邮箱，员工使用分到的邮箱。接入第三方邮箱不改变这三件事，只增加一个事实：邮箱可以不在 Zmail 的域名上。

所以模型只加一个维度。谁能用（私人或共享）沿用现有权限，从哪来（自建或接入）是新的。权限、交接、审计、AI 和 Agent 授权只看前者。

用户故事与路径

四个人，四条路

运营小王：一页看完所有账号的新信

我用几个 Gmail 注册了不同平台的账号。我想每天早上在一个地方看到所有新信，知道哪封要回。

  1. 收件箱侧栏点「＋ 接入外部邮箱」，选 Gmail
  2. 看完三条说明，选回溯范围，去 Google 授权
  3. 回到 Zmail，新邮箱出现在「我接入的」，开始回填
  4. 统一收件箱里按来源筛选；平台来信自动关联到「设计编辑部」角色
  5. 授权失效时看到提示，点一次「重新连接」恢复，历史不重复

老板老陈：给客服接入团队邮箱

support@ 一直在 Google Workspace 上。我想让客服组在 Zmail 里一起处理，但不想搬域名。

  1. 管理后台「外部连接」→「接入团队账号」
  2. 用 support@ 登录授权
  3. 在和新建共享邮箱一样的对话框里分配 4 名客服及权限
  4. 客服在各自的收件箱里看到它，各自已读
  5. 老陈自己要读信时，先把自己加为成员，留下记录

IT 小周：100 名员工一次开通

公司用 Microsoft 365。我不想让每个人自己点授权，也要在员工离职时立刻收回。

  1. 所有者完成一次管理员同意
  2. 从目录多选地址，逐行分配为私人或共享
  3. 逐行看结果，失败的行可重试
  4. 员工登录即看到自己的邮箱，无需任何操作
  5. 员工离职：邮箱进入待交接，历史封存，指定接手人

Agent：读获准的新信，做下一步

我是小王授权的运营助手。我只该看到平台来信，把需要处理的事变成待办和回复草稿。

  1. 小王在邮箱的「Agent」页签授权：范围、能力、有效期
  2. Agent 用游标拉取新信，或接收签名推送
  3. 分流：归档、待办、需要人工复核
  4. 起草回复，进入「待确认」
  5. 小王确认后才发出；每一步都能追到授权和原信
和现在的企业版怎么结合

角色不变，多管一样东西：连接

角色今天能做的接入后多出来的仍然不能做的
所有者创建组织、管理成员、分配邮箱授权和撤销企业租户；接入团队账号；强制断开任何连接不因角色读任何信；看不到员工个人账号的完整地址
管理员新建和分配邮箱、交接接入团队账号并分配成员；从已授权的租户目录里分配；强制断开不能授权或撤销租户；不能替员工开启 AI 或 Agent
成员使用分到的邮箱接入自己的账号（最多 10 个）；为自己的邮箱授权 Agent看不到别人的个人接入
共享邮箱「管理成员」增删成员、开关 webhook重新连接团队账号；为该邮箱授权 Agent不能删除邮箱或发起交接

员工离开时

邮箱发生什么理由
自建私人待交接，历史封存，管理员指定接手人地址是组织的，业务要继续
个人接入立即断开：退还授权、清除令牌、停止同步。不交接。副本到期删除账号是员工本人的。已实现
共享接入只失去成员资格连接属于组织
租户分配的私人邮箱与自建私人相同地址是组织的

名额分开算：接入邮箱不占组织的自建邮箱名额，只读期间不消耗发送额度。邮件角色（品牌身份）可以同时包含自建和接入邮箱，平台账号台账的「注册邮箱」可以指向接入邮箱。

从证据得出的八条设计结论

1. 我们必须存信

直通（Nylas、Aurinko）适合做 API 转售。统一收件箱、搜索、AI 分流和 Agent 都要本地有信，所以走 Front 和 Unipile 的路：存，但回填有上限，从新到旧。

2. 连接是一等对象，重新授权原地恢复

各家都这样做，删掉重建会丢游标和 ID。我们已这样实现

3. 推送只当提示，轮询兜底

Gmail 和 Graph 的通知都可能丢，订阅都在 7 天内过期。需要续期任务和按游标的补拉。

4. 游标按服务商的形状存

Gmail 是每账号一个 historyId；Graph 的增量是每个文件夹一个；IMAP 是每文件夹的 UID。游标过期时走「有上限的重新对齐」。需调整 现在只有一个文本游标。

5. 远端状态只同步必要的

Front 只同步新信、已发和垃圾状态，不同步已读、归档、标签。我们照此起步：已读是每人各自的，本来就不该被远端覆盖。

6. 事件至少投递一次，可重放

只靠 webhook 会丢（Nylas 超过 72 小时不补）。Agent 收件流用「稳定事件 ID + 可回放的游标」，推送只是加速。

7. Google 审核是最大的外部成本

gmail.readonly 是受限权限：需要验证加每年一次安全评估，评估费 500 到 4,500 美元，几周时间。测试模式下最多 100 人，而且授权7 天就过期，试点用户每周都得重连。

8. 企业客户可以绕开审核

Google 对「内部使用」和全域安装的应用免审核；Microsoft 可以用「应用的 RBAC」把应用权限限制到指定邮箱。所以企业走「自带应用」或租户接入，比等我们的公共应用过审更快。

对计划的影响：把「组织自带 OAuth 应用」提前到 C2，让企业试点不被 Google 审核卡住；Agent 权限照 AgentMail 的做法，按邮箱限定的密钥加能力白名单，发信一律先起草再由人确认。

已经建好的（分支 feat/mail-connectors）

  • 连接器注册表，服务商标识是数据不是表结构
  • 授权：一次性 state（只存哈希）、PKCE、10 分钟过期
  • 绑定、重连、解绑后重绑走同一条规则，不产生重复邮件
  • 外部邮箱不接收 Zmail 投递
  • 所有来源共用一个入库后处理步骤
  • 离职断开；AI 分流只有主人能开

复查发现、真实适配器之前要补的

  • 令牌轮换：拉信接口要能返回新的刷新令牌并原子保存，否则 Microsoft 账号会在一次同步后失效
  • 回填与增量分开：回填是可续跑的分页任务，带进度；增量是轻量游标。现在两者是同一次调用
  • 游标的形状：Graph 的增量是每个文件夹一个，游标要能存一组；服务商说游标太旧时，进入有上限的「重新对齐」而不是报错
  • 远端变更：已读、删除、移动要不要镜像，按邮箱一个策略
  • 附件：只存元数据，打开时再取
  • 限流：按服务商和按连接各一个预算，带退避和抖动
  • 运行记录：每次同步一条记录，供状态页和排障用

后台长任务

七个任务，都跑在现有的 PostgreSQL 任务队列上

不引入新的基础设施。每个任务都有租约、幂等键和明确的失败去向，多副本可以同时跑。

任务触发幂等靠什么失败怎么办状态
回填绑定成功；游标过期每邮箱每个服务商消息 ID 唯一；分页游标落库，可续跑退避重试；进度保留；界面显示「已同步 N 封」待做
增量同步每连接 2 分钟；或收到推送同上；连接行上的租约防止两个 worker 同时拉授权失败 → 需重新连接；其他错误 → 下个周期重试已有（轮询）
推送订阅续期到期前定时按连接一条订阅记录续期失败退回轮询，不丢信待做
令牌刷新拉信前按需新令牌与同步结果同一事务保存拒绝 → 需重新连接并通知主人待做
副本清理解绑或离职后到保留期按邮箱分批删除，可重入下次继续待做
Agent 收件投递新信入库（同一事务写入待投递）每个授权一个单调游标；推送带事件 ID重试后进入死信；拉取端不受影响待做
租户目录同步每天；管理员手动按目录对象 ID 对账只标记差异，不自动开通或回收待做
