# Zmail 工程化复盘：哪些对话是无效的，怎么做更有效

> 范围：2026-11-18 17:11 至 2026-11-20 11:37（UTC），约 42 小时。主会话 1 个，另有夜间开发循环、稳定性循环和 ⑤ 事务邮件并行会话。
> 产出：合并 PR #22–#45，共 24 个；main 新增 204 个非合并提交；生产（zmail.im，FE5）上线约 10 次，零回滚。
> 证据：主会话记录（用脚本统计，不含任何凭据）、`git log`、`gh pr list`、`docs/OVERNIGHT_LOG.zh-CN.md`、`docs/DEPLOYMENT_FE5_0083.md`、`.claude/*-loop-prompt.md`、`.claude/stability-log.md`。
> 这不是代码评审，只讨论"人和 Claude 怎么协作"。

## 一页结论

### 最重要的 5 个发现

1. **问进度是最大的单项浪费。** 126 条人工消息里有 17 条是在问状态（"现在进度怎么样了？"连问 4 次，"还要多久能完成？"2 次，"目前进展怎么样了"2 次）。每问一次，Claude 都要停下手头、重新盘点、写一大段汇报。答案本来已经写在日志和 PR 里，只是没有一个固定的地方让你看。
2. **决策是一个一个被问出来的，而不是一批一批。** 53 条人工消息不超过 12 个字，大多是在回答确认题：`选第 2 种`、`Approach A`、`方案 A`、`Approve, write plan`、`Subagent-driven`（出现 5 次）、`推送并开 PR`、`打开 Auto-fix`。直到 11-19 17:58 你说"不需要我确认吧，我要出门了"，并写出夜间循环提示词后，确认才基本消失。
3. **产品规则发现得太晚，造成返工。** 11-19 14:51 端到端测试时 Claude 已经看到"`support@` 在企业自有域名上也被拦截"，只换了个地址继续测，没有把它当成产品问题提给你。直到 11-20 11:21 你导入 zgi.app 时才说"这个是给企业用的啊，人家自己为啥建立不了呢？"，于是有了 PR #43。同类的还有 11-19 15:53 "每个邮箱应该是一个全局切换吧"，界面已经做完才推翻，重画原型后统一改（PR #28/#29）。
4. **质量门禁在最后才跑，失败就是整轮返工。** 例：公共邮箱管理（PR #41）第一次 `make check` 卡在英文源码检查，第二次卡在前端打包体积，第三次才过，每次全量检查都要十几分钟。CI 在 11-19 下午也被卡住（"目前都卡在ci 上，可以不用ci 吗"），最后靠 PR #26 把 CI 精简到最少。
5. **真正起作用的是"写下来的规则"，不是聊天。** 夜间循环提示词（`.claude/overnight-loop-prompt.md`）和稳定性循环提示词把范围、质量门槛、部署流程、禁止事项和"停下等我"条件一次写清。之后约 10 小时里，主循环自主完成 PR #35–#45，部署全部带备份、预演、冒烟和部署锁，零回滚；稳定性循环自己发现并修好了一个真 bug（PR #44，迁移排序受数据库排序规则影响）。

### 最值得做的 5 个改变（按预期收益排序）

1. **每次开工写一份"任务说明书"，不要靠多轮对话。** 写清目标、验收标准、哪些可以自己定、哪些必须停下等我。说明书就是夜间循环提示词那种格式（模板见第四节）。
2. **用一个固定的状态看板代替问进度。** 让 Claude 维护一个状态文件或 Artifact 页面（在做什么、卡在哪、待我决定、最近一次部署），你想看就打开，不用发消息问。
3. **决策攒成一批，每天看一次。** 能自己定的直接定并记成"设计决定（待确认）"；只有花钱、凭据、删除线上资源、重大方向分歧才单独打断。你每天集中看一次"待我确认"清单。
4. **开工前过一遍产品规则清单。** 尤其是多租户和域名归属：这条规则在平台共享域名上和企业自有域名上是否一样？谁是管理员？一个人能看到哪些邮箱？测试时看到"规则拦住了合理操作"必须上报，不能绕过去。
5. **把慢门禁拆成快检查，每个任务都跑。** 英文源码检查、打包体积、生成文件新鲜度这些几秒到一分钟的检查，每个任务结束就跑；`make check` 只在合并前跑一次。

## 二、有效的做法

1. **写下来的循环提示词就是唯一的任务说明书。** `.claude/overnight-loop-prompt.md` 只有 45 行，但包含：开工先从 git/PR/日志恢复现场（防止上下文压缩后重做）、按顺序的任务清单、每块的质量门槛、部署流程、绝对不做、停下等我。之后 10 小时（11-20 01:00–11:37）合并了 PR #35–#45，你只发了 6 条消息。
2. **部署锁 + 迁移预演 + 冒烟 + 回滚预案。** 每次部署：先备份 → 有迁移就在一次性容器里预演，新旧两个 API 镜像都要能启动 → 版本化镜像、旧镜像保留 → 先换 API 和 worker，再换 web → 冒烟 → 写部署记录。两个循环会话靠 `.deploy-lock` 互斥。约 10 次生产变更零回滚；例如 PR #41 的索引迁移预演 44 ms，生产 58 ms，事先就知道不会锁表。
3. **独立的稳定性循环抓到了真 bug。** 它不开发新功能，只巡检和回归。第 4 轮发现 `TestProperty1_RepositoryGetRanOrdering` 偶发失败，追到根因是迁移名按数据库排序规则（忽略下划线）而不是字节序排序，先写必定复现的测试再修，PR #44。还修了 Kest 流程的配置问题（PR #37）。
4. **每个切片走"设计文档 → 实施计划 → TDD → 逐任务审查"。** 例如验证码遮罩（PR #36）：设计决定 D1–D6 先写成"待确认"、不停下，实施时先写失败测试，Kest 15/15、Web 823 个测试、1440×900 浅色和深色都看过才合并。标签死锁（11-19 14:22）就是逐任务审查发现的。
5. **一个切片一个 PR，合并后立刻部署。** 11-19 20:40 你说"开发完成后及时提交，push 合并到主分支"之后，PR 粒度变小，问题定位快，回滚预案也简单。
6. **汇报格式固定为"做了什么 / 正在做 / 接下来"，全程中文。** 写进了记忆，后面的汇报一致、可扫读。
7. **敏感操作的边界写得清楚。** 不用生产 Cloudflare 凭据做测试、不在生产用密码登录、不真实发信。Claude 在 11-19 14:40 主动拒绝拿生产凭据做本地测试，11-20 11:20 也明确说导入的最后一步要你在后台完成。

## 三、具体改进（按预期收益排序）

### 1. 用"任务说明书"开工（收益最大）

一次写清，比 30 轮确认省得多。必须包含：

- **目标：** 用户能做成什么事（不是"做 X 功能"）。
- **验收标准：** 怎么算完成，例如"企业管理员在 zgi.app 上能建 support@；导入 61 行 CSV 全部通过"。
- **可以自己定的：** UI 细节、命名、实现方式、任务顺序、推送 / 开 PR / 合并 / 部署（按部署流程）。
- **必须停下的：** 花钱、新凭据、外部账号、删除线上资源、改需求范围、两个方案差异大且没有明显更优。
- **不做什么：** 明确划出范围外的事。

模板见第四节。

### 2. 固定的状态看板，代替问进度

- 让 Claude 维护一个状态页（Artifact 或仓库里的 `docs/STATUS.zh-CN.md`），每完成一块就更新，只保留最新状态：
  - 切片编号对照表（①–⑤ 各是什么、状态）；
  - 正在做什么、卡在哪；
  - 待我确认清单；
  - 最近一次生产部署（提交、镜像、时间、冒烟结果）；
  - 稳定性巡检最近一轮结果。
- 你想看就打开，不发消息。预期可省掉 17 次问进度中的大部分。

### 3. 决策攒成一批

- 能自己定的直接定，写成"设计决定（待确认）"并继续做，正如验证码遮罩 D1–D6 的做法。
- 看板上的"待我确认"清单每天看一次，一次回复全部："D1 同意，D3 改成……，其余同意"。
- 只有第 1 条"必须停下"的情况才单独打断。

### 4. 开工前过一遍产品规则清单

每份设计文档加一节，逐条回答：

- **角色：** 平台运营方、企业管理员、企业员工、外部开发者，各能做什么、看什么？
- **域名归属：** 这条规则在 Zmail 共享域名上和企业自有域名上是否不同？（support@ 就栽在这里）
- **多租户隔离：** 一个组织能否看到、影响另一个组织的数据？
- **上限和配额：** 默认值是多少，谁能改？（11-20 11:20 邮箱上限 50 不够，临时调到 200）
- **对标产品：** Gmail / Outlook / 飞书是怎么做的？（多邮箱切换就是事后才对标的）

测试规则：**测试中发现"规则拦住了合理操作"，必须作为产品问题记进待我确认清单，不能换个数据绕过去。**

### 5. 减少通知噪音

- 后台任务只在"完成、失败、需要决定"三种情况唤醒主会话；"还在跑"写进看板。
- 子会话的结果汇总到看板，主会话不逐条转述。
- 多个全量检查同时跑时，合并成一条汇报。

### 6. 把门禁前移

- 每个任务结束就跑快检查（几秒到一分钟）：英文源码检查、打包体积、生成文件（golden schema、`openapi.ts`、模块 README）新鲜度、`make agent-check-changed`。
- `make check` 只在合并前跑一次。
- 可以把这些快检查做成一个 `make quick-check`，写进循环提示词的质量门槛。

### 7. 开工前的 agent 环境检查清单

在第一个循环开始前确认一次，省掉中途卡住：

- 子代理的 worktree 能执行 git（commit、push）；
- 可用的模型别名（`sonnet` 在本环境不可用就直接写 opus）；
- 测试数据库（`127.0.0.1:55450`）和 Kest 的 `.kestenv` 约定可用；
- 用量余量，长任务前避开快到上限的时段；
- 定期清理 `.claude/worktrees/` 下已合并的工作树；
- 已知的基础设施风险（共享库连接数）先找你决定处理方式，不要让它在每次部署时重试。

### 8. 并行分支控制在 2–3 个

18 个"把 main 合进分支"的同步提交说明同时开的分支太多。同时最多 2–3 个，且尽量不碰同一批生成文件（golden schema、`openapi.ts`）。

### 4.2 循环提示词骨架

```text
<一句话目标>。我不在，过程中不用问我；只在第六节的情况停下。全程中文。
状态看板：<路径>，每完成一块就更新（做了什么 / 正在做 / 接下来 / 待我确认 / 最近部署）。

一、每轮开始先恢复现场
- 以 git 和 GitHub 为准，不靠记忆：fetch，看 main 最新提交、已合并 PR、看板最后一条。
- 已合并或已部署的不重做；做到一半的分支接着做。

二、任务清单（按顺序）
1. <任务>（验收标准：...）
2. <任务>（验收标准：...）

三、每块的质量门槛
- 先写失败测试；Bug 先写复现测试。
- 每个任务结束跑快检查（英文源码、打包体积、生成文件、agent-check-changed）。
- 合并前跑一次 make check；接口跑 Kest；界面看浅色和深色。
- 设计文档必须过产品规则清单（角色、域名归属、多租户、上限、对标）。
- 测试中被规则挡住的合理操作，记进"待我确认"，不要绕过。
- 一块一个 PR，合并后立刻部署。

四、部署流程
- 拿部署锁 → 备份 → 有迁移就预演（新旧镜像都健康）→ 版本化镜像 → 先 API/worker 后 web → 冒烟 → 失败回滚 → 写部署记录 → 释放锁。

五、绝对不做
- <凭据、删除、花钱、真实发信、生产登录、改写历史、强推等>

六、停下等我（写清原因和需要我做什么）
- 冒烟失败已回滚，或回滚失败。
- 需要钱、新凭据、外部账号、删除线上资源。
- 重大产品方向分歧。
- 全部可做的都做完了：写总结（PR、镜像、未完成项、待我决定）。

七、节奏
- 后台任务只在完成、失败、需要决定时唤醒；其他时间约 30 分钟一轮。
```
