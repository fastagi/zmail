# 邮箱权限功能需求文档

本文档确认后，进入架构设计（按 [BUSINESS_IMPLEMENTATION_PLAN_STANDARD.md](BUSINESS_IMPLEMENTATION_PLAN_STANDARD.md)），再拆任务实现。

## 1. 为什么做

今天一个组织里的所有邮箱对所有成员可见、可发。员工自己的验证码、找回密码和私信不能因为集中管理而对全组织可见；业务邮箱也应只让真正负责的人处理。本功能让每个邮箱有明确的使用者，并保证任何入口都不能绕过。

**成功的样子**：两名员工各有私人邮箱，共同处理一个共享邮箱。从列表、未读数、搜索、正文、附件、链接、API 和 webhook 任一入口交叉尝试，看不到不属于自己的信；员工离职后，地址继续接收业务邮件，离职前的私信不被任何人看到。

**目标**
- 私人邮箱只有主人能读能发。
- 共享邮箱按人授予权限，权限只有“查看”“回复”“管理成员”三级。
- 组织管理员能管理邮箱和成员，但读信必须留下记录。
- 员工离职时，地址可交接，历史私信封存。
- 每人各自的已读和未读。

**不做（本期）**：别名和批量开通、Gmail/Outlook 绑定（R2）、Agent 读信授权和 AI 分流（R4）、全组织审计页、按组或部门授权。这些后续功能必须使用本文档定义的同一套权限规则，不得另开入口。

**反目标**（技术上能用，但算失败）
- 管理员不留痕迹就能读到任何邮箱的信。
- 任何一个入口（包括 webhook、API key、统计、搜索）泄露无权邮箱的主题、发件人、收件人或数量。
- 交接后接手人或管理员能看到离职员工的历史私信。

**前提**：产品尚未正式上线，没有需要兼容的真实用户，不做迁移预览功能。

## 2. 概念

| 概念 | 定义 |
|---|---|
| 私人邮箱 | 属于一位组织成员（主人）。只有主人能查看和回复。不能加入其他人，主人也不能把它改为共享。 |
| 共享邮箱 | 由一组成员共同使用。每位成员有一个权限级别。 |
| 查看 | 列出和打开信件、下载附件、标记自己的已读或未读。 |
| 回复 | 包含“查看”；另外可用该地址发信、回复、删除信件，以及作为广播或模板试发的发件邮箱。 |
| 管理成员 | 包含“回复”；另外可增删该共享邮箱的成员、修改他们的权限、查看权限变更历史。 |
| 组织管理员 | 组织的 owner 和 admin 角色。 |
| 交接 | 私人邮箱的主人离开组织（或管理员提前发起）后，把地址转给接手人。 |
| 封存历史 | 交接时点之前、私人邮箱里的全部信件。任何人不可读。 |

## 3. 规则

### 3.1 开通

- 只有组织管理员能新建邮箱，新建时必须选择类型：
  - 私人邮箱必须指定一位主人，主人必须是当前组织成员。
  - 共享邮箱必须至少指定一位成员及其权限。
- 员工不能自己开通任何邮箱。
- 每组织最多 50 个邮箱（现有上限不变）；每个共享邮箱最多 100 位成员。

### 3.2 组织管理员

- 能看到组织里的所有邮箱：地址、类型、主人或成员名单、状态。
- 能新建、删除邮箱；能增删共享邮箱成员和修改权限；能发起交接；能彻底删除封存历史。
- **不会因为角色自动看到任何信件。** 列表里对无查看权的邮箱不显示未读数和任何信件信息。
- 要读或发共享邮箱的信，管理员必须先把自己加为成员。这一操作和其他成员变更一样写入变更历史。
- 管理员不能把自己加入私人邮箱，也不能把私人邮箱改为共享（交接除外）。

### 3.3 共享邮箱成员

- 按自己的权限级别使用邮箱。
- 有“管理成员”权限的成员可以增删成员、修改权限（包括授予“管理成员”），但不能删除邮箱，不能把邮箱改为私人邮箱，不能发起交接。
- 只能把当前组织成员加入共享邮箱。

### 3.4 私人邮箱主人

- 能查看和回复自己的私人邮箱。
- 不能加入他人，不能改为共享，不能删除邮箱（删除由管理员执行）。
- 需要协作时，由管理员另开共享邮箱。

### 3.5 离开组织与交接

- 成员离开组织的那一刻，立即失去所有邮箱的访问权；其在共享邮箱的成员资格同时作废。
- 主人离开组织后，其私人邮箱进入“待交接”状态：
  - 地址继续收信，新信不丢失。
  - 在指定接手人之前，没有任何人能读这个邮箱。
- 管理员为“待交接”邮箱指定一位接手人（必须是当前组织成员）。完成交接后：
  - 邮箱转为共享邮箱，接手人获得“回复”权限。
  - **封存边界是原主人失去访问的时刻**（离开组织，或管理员提前发起交接的时刻）。边界之前的信封存，任何人（包括接手人和管理员）都看不到，也不出现在搜索、统计和未读数中；边界之后到达的信对接手人可见。
  - 封存按信件判断：边界之前收到和发出的信、它们的附件和投递事件（包括边界之后才到达的退信等事件）全部封存，不推送 webhook；边界之前从该邮箱发起的广播，详情和收件人结果同样封存。
  - 以后更换接手人或增加成员，按共享邮箱的普通成员变更处理。
- 管理员也可以在员工离职前对其私人邮箱发起交接，效果相同，原主人立即失去访问权。
- 原主人重新加入组织：
  - 若邮箱仍是“待交接”，邮箱自动归还给他，恢复为私人邮箱，封存解除，他能看到全部历史和待交接期间到达的信。归还写入变更历史。
  - 若已交接给他人，不归还；封存历史继续封存。
  - 他原有的共享邮箱成员资格不自动恢复，由管理员重新添加。
- 封存历史默认永久保留，不自动删除。管理员可以彻底删除某个邮箱的封存历史：需二次确认，不可恢复，并写入变更历史。

### 3.6 已读与未读

- 每人每封信各自有已读状态。一个人打开信只对他自己变为已读。
- 邮箱列表未读数、“今日新到”“未读”筛选都按当前登录的人计算。
- 一个人失去某邮箱的访问权后，他在该邮箱的已读记录清除。
- 用 API key 读取信件不改变任何人的已读状态。
- “谁已经处理了这封信”不由已读表达，留给 R4 待办状态。

### 3.7 各入口的统一要求

所有入口按同一规则判断，不能有例外：

| 入口 | 要求 |
|---|---|
| 邮箱列表 | 普通成员只看到自己能访问的邮箱；管理员看到全部，但无查看权的邮箱没有未读数和信件信息 |
| 信件列表、正文、附件、直接链接 | 需要“查看” |
| 标记自己的已读/未读 | 需要“查看” |
| 发信、回复、删除信件 | 需要“回复” |
| 全局信件记录与搜索、每日统计 | 只包含有“查看”权的邮箱；封存历史一律排除 |
| 广播草稿（创建、修改） | 原有角色要求不变（成员即可），另外需要发件邮箱的“回复” |
| 广播开始发送、恢复发送 | 原有角色要求不变（组织管理员），另外需要发件邮箱的“回复”；管理员需先把自己加为该邮箱成员 |
| 广播暂停、取消 | 原有角色要求不变，不需要邮箱权限 |
| 查看广播（列表、详情、收件人结果） | 需要发件邮箱的“查看” |
| 模板试发 | 原有角色要求不变，另外需要发件邮箱的“回复” |
| 组织发送额度用量 | 只向组织管理员显示具体数字；成员发信被额度挡住时只提示“额度已满，排队中” |
| API key 发信 / 查已发信 | key 的主人需要发件邮箱的“回复” / “查看” |
| 组织 webhook | 见 3.8 |

被拒绝时的表现：对该邮箱**没有任何权限**的人，系统表现为“邮箱不存在”，不暴露它的存在；**有部分权限但不够**的人，提示“无权限”。

权限在开始发送（含定时发送的设定时刻）和恢复发送时检查。一封已开始或已排定的广播，在发起人失去“回复”权限后照常发完；管理员可以暂停或取消，恢复时重新检查。

“管理员读信必须留下记录”指的是 3.9 的变更历史（谁在何时给自己开了权限），不对每次打开信件单独记日志。

### 3.8 组织 webhook

- 私人邮箱的信件事件永不推送到组织 webhook。
- 共享邮箱默认不推送。有“管理成员”权限的人可以为该邮箱开启“推送到组织 webhook”，开启和关闭都写入变更历史。开关覆盖该邮箱的全部信件事件（收信、发出、送达、退信、投诉等）；后端服务用 API key 发信并追踪退信时，应使用开启了推送的共享邮箱。理由：webhook 地址由组织管理员配置，默认推送等于让管理员不留痕迹地拿到主题和收发件人。

### 3.9 变更历史

- 每个邮箱有一份权限变更历史：新建、类型、成员增删、权限修改、交接、webhook 开关、封存历史删除。每条记录写明谁、什么时间、改了什么。
- 历史对组织管理员可见；共享邮箱的历史也对该邮箱“管理成员”可见；私人邮箱的历史也对其主人可见。
- 历史只记权限事实，不含任何信件内容。

### 3.10 现有数据

- 生产环境的现有邮箱在上线时一次性转为共享邮箱：创建者获得“管理成员”权限；其余成员由管理员按需添加。这一步是一次性的运维动作，不做成产品功能。
- 现有已读状态视为创建者本人的已读状态。

## 4. 界面要求

- 邮箱列表用图标区分私人、共享、待交接。无查看权的邮箱显示为锁定状态，不能点进信件列表。
- 没有“回复”权时，不显示写信、回复、删除按钮。
- 邮箱的“权限”面板：类型、主人或成员及其权限、webhook 开关、变更历史。有权限的人可以在面板里操作。
- 待交接邮箱在面板里显示“指定接手人”，并说明封存规则。
- 删除封存历史前弹出二次确认，写明不可恢复。
- 中英文文案都要提供。

## 5. 验收用例

准备：组织 O，管理员 A，员工 B 和 C。B 有私人邮箱 `b@`，C 有私人邮箱 `c@`；共享邮箱 `team@`，B 为“回复”，C 为“查看”。每个邮箱各有一封带附件的来信。

| 编号 | 操作 | 预期 |
|---|---|---|
| AC-1 | C 依次访问 `b@` 的邮箱列表项、信件列表、正文、附件链接、标记已读、发信 | 列表中没有 `b@`；其余全部表现为“邮箱不存在”，不返回任何内容 |
| AC-2 | A 打开邮箱列表，再打开 `b@` 的信件 | 列表中有 `b@`，但无未读数；打开信件表现为“无权限” |
| AC-3 | A 在全局记录中搜索 `b@` 那封信的主题；查看每日统计 | 搜索结果为 0；统计不含 `b@` 的数量 |
| AC-4 | C 在 `team@` 读信、发信 | 读信成功；发信“无权限”，不产生任何信件，不消耗发送额度 |
| AC-5 | B 和 C 都能看 `team@`；B 打开一封新信 | B 的未读数减 1，C 的未读数不变 |
| AC-6 | C 用自己的 API key 以 `team@` 发信；以 `b@` 发信 | 前者“无权限”，后者“邮箱不存在”；都不产生信件，不消耗额度 |
| AC-7 | A 给自己加 `team@` 的“查看”后读信 | 读信成功；`team@` 变更历史出现“A 给 A 授予查看”及时间 |
| AC-8 | B 有“回复”无“管理成员”时尝试加成员；A 授予 B“管理成员”后 B 再加人 | 前者“无权限”；后者成功并写入历史 |
| AC-9 | 向 `b@`、`team@`（未开启推送）、`team@`（开启推送后）各投递一封信 | 组织 webhook 只收到开启推送后那一封 |
| AC-10 | B 离开组织 | B 的所有请求失败；`b@` 变为“待交接”；新投递到 `b@` 的信被接收但无人可读 |
| AC-11 | A 指定 C 接手 `b@` | `b@` 变为共享，C 为“回复”；C 只看到 B 离开之后到达的信，搜索和统计中也只有这些；A 和 C 都看不到之前的信 |
| AC-12 | A 删除 `b@` 的封存历史 | 二次确认后删除；不可恢复；历史中记录删除动作和时间 |
| AC-13 | B 用 `team@` 建广播草稿；A 未加入 `team@` 时开始发送；A 给自己加“回复”后开始发送，发送中 A 移除自己的成员资格 | 草稿成功；第一次开始发送“无权限”；第二次成功并写入历史，移除后广播继续发完，A 仍可暂停或取消 |
| AC-16 | B 离开后、交接前重新加入组织 | `b@` 恢复为 B 的私人邮箱，B 能看到全部历史和期间新信；`team@` 不自动恢复；历史记录“归还” |
| AC-17 | B 离开、A 交接给 C 之后 B 重新加入 | `b@` 仍归 C；B 看不到 `b@`；封存历史仍无人可读 |
| AC-15 | C 查看 `b@` 发出的广播列表、详情和收件人结果 | 列表中没有；详情和收件人表现为“不存在” |
| AC-14 | 员工 B 尝试新建邮箱；A 新建私人邮箱不指定主人；A 新建共享邮箱不指定成员 | 全部被拒绝并说明原因 |

所有越权尝试的成功次数必须为 0。

## 6. 本文档做出的默认决定

以下是对齐过程中我提出、你未提出异议而采用的决定，确认文档时请留意：

1. 交接后接手人获得“回复”而不是“管理成员”；成员变更由管理员负责。
2. 共享邮箱默认不推送组织 webhook，需由“管理成员”开启（因为已取消“全组织共享”模式，原“全组织邮箱照常推送”的提议不再适用）。
3. 封存边界是原主人失去访问的时刻；待交接期间到达的新信属于边界之后，交接后对接手人可见。
4. 每个共享邮箱最多 100 位成员。
5. 现有生产邮箱的已读状态归创建者所有。
6. 管理员要从某个邮箱发广播，需先把自己加为该邮箱的“回复”成员（由管理员读信需留痕的决定推出）。
7. 查看广播需要发件邮箱的“查看”；组织发送额度的具体用量只给管理员看。
8. 封存按信件判断，覆盖收发信件、附件、投递事件和边界前的广播。
9. “留下记录”指权限变更历史，不记录每次打开信件。
